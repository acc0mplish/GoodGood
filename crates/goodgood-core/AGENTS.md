# goodgood-core 에이전트 지침

모듈 책임은 `docs/architecture/core.md`를 참고합니다.

- NT 네이티브 인터페이스와 Win32 API만 사용하고 WMI는 도입하지 않습니다. 표준 사용자 권한으로 동작하는 것이 전제이므로, 열 수 없는 프로세스나 장치는 성능 저하로 처리하고(해당 항목을 비움) 오류로 보고하지 않습니다.
- UI와 무관하게 유지하고 데이터 구조를 직렬화 가능하게 만듭니다. 권한 있는 서비스 프로세스도 이 crate를 호출하며 결과는 IPC를 거쳐 인터페이스로 전달됩니다.
- serde 타입을 바꾸면 네이티브 인터페이스 모델 적응과 관련 테스트를 함께 고칩니다.
- 샘플링은 샘플링 스레드에서 수행하며 전체 샘플링에 약 19–25 ms가 걸립니다. 새 수집 항목은 소요 시간을 측정하며, 비용이 큰 항목은 요청 시 조회(`details.rs` 방식)나 캐시 후 가끔 새로 고침(`services.rs`, `meta.rs` 방식)으로 바꿉니다.
- 관리자 권한이나 드라이버 없이 읽을 수 있음을 확인한 항목: PDH `\Processor Information(*)\Actual Frequency`와 `% Processor Performance`, `\Thermal Zone Information(*)\High Precision Temperature`, `\Energy Meter(*)\Power`(RAPL, 단위 mW), 배터리 클래스 드라이버 IOCTL(SetupDi로 장치 열거), 액세스 권한이 0인 핸들로 조회하는 `StorageDeviceTemperatureProperty`(NVMe, SATA, ATA 버스만, 다음 항목 참고), D3DKMT의 노드 및 어댑터 성능 데이터(NVIDIA는 전압과 전력을 제공하지 않음), NVML의 보드 전력과 전력 상한(`System32\nvml.dll`, RTX 4060 노트북 GPU 실측), PDH `\GPU Engine(*)\Utilization Percentage`와 `\GPU Process Memory(*)`(프로세스별 GPU, 모든 프로세스에서 읽을 수 있음).
- Windows는 Intel의 E 코어와 LP E 코어에 같은 `EfficiencyClass`를 부여하며(Meteor Lake에서의 보고이고 `SchedulingClass`는 문서화되어 있지 않으므로 의존하지 않음), `cpu.rs`의 `core_kinds`는 효율 코어가 나머지 코어가 공유하는 L3 안에 있는지로 구분합니다. 근거는 Intel이 Meteor Lake용으로 제시한 CPUID.1A + CPUID.4 판단이며, Intel은 이 방법이 이후 세대에도 보장되지 않는다고 밝혔으므로 새 세대의 하이브리드 아키텍처 프로세서가 나오면 캐시 토폴로지를 확인하고 필요한 경우 모델별로 보충합니다. 개발 머신(i5-13500HX)에는 LP E 코어가 없어 이 경로는 단위 테스트와 모의 스냅숏으로만 검증됩니다.
- 로그온 세션은 `WTSEnumerateSessionsExW`(`sessions.rs`)로 읽습니다. 표준 권한으로 모든 세션의 계정 이름과 도메인을 반환하고 연속 호출에 약 40 µs, 0.5초 간격 호출에 약 0.3 ms(가끔 수 ms)가 걸리므로 약 2초마다 한 번 읽습니다. 이 호출에는 시간 제한이 없어 샘플링 중에는 `SessionTracker`의 읽기 스레드가 수행하고 샘플링 스레드는 최신 결과만 가져오며, 샘플링 스레드에서 동기 호출로 되돌리지 않습니다. 다른 사용자와 시스템 계정 프로세스의 토큰은 표준 권한으로 열 수 없으므로 프로세스를 세션 번호로 사용자에게 귀속시키고, 이를 위해 프로세스마다 토큰을 읽거나 SID를 해석하지 않습니다. `windows` crate에서 `Win32_System_RemoteDesktop`을 켜지 않았으므로 이 두 함수와 `ProcessIdToSessionId`는 `extern`으로 선언합니다. `sessions::sign_out`은 실제로 사용자를 로그오프시키므로 개발 머신에서 호출하지 않고 `ExitWindowsEx`, `WTSLogoffSession`까지 실행되는 테스트도 작성하지 않으며, `sessions_to_end`의 세션 선별만 시험합니다. 인터페이스 흐름은 모의 스냅숏으로 확인하고 실제 로그오프는 사용자가 가상 머신에서 점검합니다.
- 디스크의 `StorageDeviceTemperatureProperty`와 NVMe 프로토콜 조회(`Storage*ProtocolSpecificProperty`)는 저장 컨트롤러의 미니포트 드라이버가 처리하며 시간 제한이 없고 한 번 보낸 뒤에는 사용자 모드에서 취소할 수 없습니다. Intel RST 같은 RAID 드라이버가 요청을 완료하지 않으면 컨트롤러 전체와 시스템 디스크가 응답을 멈춰 컴퓨터가 멈추고, 블루 스크린도 없이 이벤트 로그와 `goodgood.log`조차 디스크에 기록되지 않습니다. 두 조회는 `disk::temperature_query_allowed`와 `disk_details::io::probe_nvme`가 허용한 버스로만 보내고 RAID 버스로 넓히지 않습니다. 타사 저장 장치나 그래픽 카드 드라이버에 도달하는 새 조회를 추가하기 전에 Windows 자체나 널리 쓰이는 도구가 같은 종류의 장치에 그 요청을 정상적으로 보내는지 먼저 확인하고, 확인할 수 없으면 버스나 드라이버로 범위를 제한합니다. 개발 머신에서 정상이라는 사실이 다른 저장 드라이버에서도 안전하다는 뜻은 아닙니다.
- 타사 SDK의 DLL(IGCL, ADL, NVML)은 언로드 전에 콜백이 남지 않았는지 확인합니다. `ControlLib.dll`이 등록하는 ETW 공급자는 `ctlClose`와 언로드로 해제되지 않아 Intel 그래픽 카드가 없는 머신을 한 번 충돌시켰고, 지금은 `Library::pin`으로 고정합니다. 이런 충돌을 조사할 때는 "애플리케이션" 이벤트 로그의 Application Error 1000과 `%LOCALAPPDATA%\CrashDumps`의 덤프를 확인합니다. 입력기 등이 주입한 CrashRpt는 예외를 먼저 가로채 "Error launching CrashSender.exe" 대화 상자를 띄우는데, 이런 대화 상자는 GoodGood의 것이 아닙니다.
- 코어별 온도, CPU 전압처럼 MSR이나 SMU를 읽어야 하는 데이터는 권한 있는 서비스의 PawnIO 고정 모듈로만 읽고(지원 범위는 `docs/guide/hardware-data.md` 참고) 다른 경로를 찾지 않습니다.
- 프로세스별 네트워크(`net_process.rs`)는 실시간 ETW 세션을 쓰며 시작에 해당 권한이 필요합니다. 표준 권한에서 로컬 시작이 실패하면 호스트가 권한 있는 서비스를 통해 누적 카운트를 비동기로 읽고, 두 출처를 모두 쓸 수 없을 때만 네트워크 열을 숨깁니다. GUI의 `GoodGood Network` 세션과 서비스의 `GoodGood Service Network` 세션은 빌드에 따라 구분되며 서로 중지할 수 없습니다. 세션은 프로세스보다 오래 살아남으므로 시작할 때 같은 이름의 잔여 세션을 정리하고, GUI 종료와 업데이트 설치 전에는 `stop_network_session`이 로컬 세션을 중지하며, 서비스는 임대가 끝나거나 종료할 때 tracker를 소멸시킵니다.
- `windows` crate의 기능은 루트 `Cargo.toml`의 `[workspace.dependencies]`에 모아 두고 새 기능은 거기에 추가하며 이 crate에는 추가하지 않습니다. GPUI Kit을 업그레이드한 뒤에는 `cargo tree -p goodgood -i windows -e features`로 확인하지 않으면 `windows`를 한 벌 더 컴파일합니다.
- 프로세스 상태를 바꾸는 작업(끝내기, 우선 순위, 효율성 모드, 일시 중단과 다시 시작)은 모두 `actions::open_instance`로 PID와 시작 시간을 검증합니다(PID 재사용 방지). 끝내기와 일시 중단은 핵심 시스템 프로세스를 차단하고, 일시 중단은 `actions::essential_image`에 나열된 프로세스도 차단합니다. Windows가 동결한 앱 패키지(`process::frozen`)의 스레드도 일시 중단으로 표시되지만 `NtResumeProcess`로 해제할 수 없으므로 이들에 대해서는 다시 시작을 제공하거나 실행하지 않습니다.
- `handles::scan`은 종료할 수 있는 보조 프로세스에서만 실행하고 인터페이스, 샘플링이나 서비스 스레드에 직접 넣지 않습니다. `NtQueryObject`, 파일 정보 조회, 복제한 파일 핸들의 닫기조차 블록될 수 있으므로 `goodgood-service::handles`의 Job과 시간 초과 감시가 회수합니다. 핸들은 복제해서 조회만 하고 원본 프로세스의 핸들은 절대 닫지 않습니다. 파일 사용 결과를 병합하거나 끝낼 때는 PID와 시작 시간을 유지합니다.
- `process.rs`는 실행 중인 프로세스 인스턴스마다 `PROCESS_QUERY_LIMITED_INFORMATION` 핸들 하나를 캐시합니다(효율성 모드 읽기용). 스냅숏의 스레드 수가 0이 되면 즉시 닫고 프로세스가 사라지면 항목과 함께 닫습니다. 스레드가 0인 기록에는 캐시 핸들을 만들지 않으며 최종 CPU와 I/O 카운트는 여전히 스냅숏에서 읽습니다. 샘플링마다 새로 여는 방식으로 바꾸지 않습니다.
- 규칙 엔진(`rules.rs`)은 `goodgood-service::RuleRunner`의 별도 호스트 스레드가 구동합니다. 샘플링 스레드는 최신 PID, 시작 시간과 이름만 넘기고 서비스 RPC가 샘플링을 막지 않게 합니다. 규칙 저장이나 실행 권한 출처가 바뀌면 다시 확인하고 다시 계산하며, 같은 회차에서 프로세스 인스턴스 하나에는 한 번만 적용하고 전송 실패는 자동으로 재생하지 않습니다.
- 수집 동작을 고칠 때는 관련 예제로 결과를 확인하고(명령은 `docs/development/README.md`의 "수집 데이터 검증" 참고), `history.rs`의 기록, 인코딩이나 쓰기 경로를 고칠 때는 `--example history --release -- <초>`로 기록 비용과 프레임 크기를 확인합니다.
- 기록 파일 형식(`history.rs`)을 바꿀 때는 `MAGIC`의 버전 번호를 올리고 호환 읽기와 쓰기를 확인합니다. 현재 새 파일은 v3을 쓰고 이미 있는 당일 v2 파일은 원래 형식으로 이어 쓰며 읽기는 v2와 v3을 지원합니다. 예전 기록에 없는 생성 시간은 알 수 없음으로 둡니다. v3 항목을 v2 파일에 덧붙이지 않고 신원을 채우기 위해 예전 기록을 다시 쓰지도 않습니다.
