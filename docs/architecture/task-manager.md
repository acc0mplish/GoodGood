# 시스템 작업 관리자 대체

GoodGood은 기본적으로 꺼져 있는 시스템 작업 관리자 대체를 제공합니다. 인터페이스 진입점은 "설정 → 권한"에 있고, 릴리스 버전이면서 권한 있는 서비스가 현재 계정에 승인되어 있을 때만 켤 수 있습니다. 켜려면 관리자 권한 승인이 필요하고, 끌 때는 권한 있는 서비스를 먼저 사용하며 서비스를 쓸 수 없으면 관리자 유지 관리 보조 프로그램을 사용합니다.

## 시작 경로

`HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Image File Execution Options\taskmgr.exe`의 `Debugger` 값을 고정으로 수정하며, 종류는 `REG_SZ`이고 내용은 따옴표로 감싼 독립 런처 절대 경로와 `--task-manager`입니다. 다른 값, 키 권한이나 시스템 실행 파일은 수정하지 않습니다. 기존 Debugger(빈 값 포함), UseFilter 또는 하위 키를 발견하면 사용 설정을 거부합니다. 이때 상태 설명에는 발견한 항목이 무엇인지(Debugger 값, UseFilter, 앞 몇 개 하위 키의 이름과 총수) 적고, 진단 로그에는 분류만 기록하며(Debugger가 GoodGood 런처, 다른 프로그램, 비어 있음 또는 텍스트가 아닌 종류를 가리키는지, UseFilter, 하위 키 수와 그중 `PerfOptions` 존재 여부) 값은 기록하지 않습니다.

IFEO는 디버거 접두사를 `taskmgr.exe`를 대상으로 하는 시작 명령에 붙이므로 바로 가기와 직접 실행을 포함해 컴퓨터 전체의 모든 진입점에 영향을 줍니다. Windows 11은 WOW64 뷰 사이에서 이 레지스트리 분기를 공유합니다. [IFEO 시작 설명](https://devblogs.microsoft.com/oldnewthing/20070702-00/?p=26193/)과 [WOW64 레지스트리 규칙](https://learn.microsoft.com/en-us/windows/win32/winprog64/shared-registry-keys)을 참조하십시오.

런처와 독립 복구 프로그램은 GoodGood 릴리스 프로그램에서 추출해 관리자와 SYSTEM만 쓸 수 있는 `GoodGood Privileged` 디렉터리에 설치합니다. IFEO 자체 점검을 통과하면 인터페이스 프로그램을 버전별로 같은 디렉터리에 복사합니다. 사용 설정에 실패하면 이번 사본을 정리하고, 이후 유지 관리에서는 이미 종료되었고 복구 기록이 참조하지 않는 사본만 정리합니다. 로그인 시작 항목은 설치된 `goodgood.exe`를 가리킵니다. 설치 버전이 시작할 때는 구버전이 써 둔 사본 경로도 함께 바로잡습니다.

런처는 승인 계정에 대해서만 GoodGood 시작을 시도하고 다른 계정에는 네이티브 작업 관리자를 바로 시도합니다. 시작 진입점은 먼저 호출자 세션에서 표준 권한으로 실행됩니다. [관리자 권한 실행](administrator-startup.md)이 켜져 있으면 단일 인스턴스와 주 창을 만들기 전에 같은 계정, 같은 세션의 관리자 작업으로 넘깁니다. 꺼져 있으면 일반 권한을 따릅니다. 권한 상승하지 않은 런처는 인터페이스를 직접 만들고, 권한 상승한 런처(예를 들어 관리자 명령 프롬프트에서 `taskmgr`을 실행)는 인터페이스를 데스크톱 셸(탐색기)의 자식 프로세스로 만들며(`PROC_THREAD_ATTRIBUTE_PARENT_PROCESS`) 인터페이스는 셸의 표준 토큰을 상속합니다. 셸을 찾지 못하거나 셸이 같은 계정이 아니면 네이티브 경로로 돌아갑니다. 계정에 분할 토큰이 없으면(UAC 끔, 기본 제공 Administrator 계정) 토큰이 하나뿐이므로 인터페이스는 평소처럼 그 토큰으로 실행됩니다. 인터페이스의 환경 변수는 생성자의 환경을 잇지 않고 현재 계정으로 다시 만듭니다.

권한 상승 토큰의 연결 토큰(`TokenLinkedToken`)은 SeTcbPrivilege로 제한됩니다. 이 권한이 없으면 식별 수준 토큰을 얻게 되고 Windows는 그것으로 기본 토큰을 만들지 거부합니다(`ERROR_BAD_IMPERSONATION_LEVEL`, 표준 권한에서 제한된 토큰의 연결 토큰으로 실측). 분할 토큰이 없는 계정에는 얻을 연결 토큰이 없습니다.

인터페이스 자체 점검은 PID, 생성 시간, 계정과 세션으로 요청 프로세스를 검증한 뒤 그 프로세스를 부모로 삼아 자체 점검 인스턴스를 만들고 토큰을 상속합니다. UAC가 다른 계정의 자격 증명을 써도 대화형 인터페이스는 원래 계정에서 실행됩니다. 유지 관리 보조 프로그램은 필요할 때 `SeDebugPrivilege`를 켜서 요청 프로세스를 열고 토큰을 조회해 계정을 확인합니다.

인터페이스 호출에는 독립된 준비 핸드셰이크가 있고 프로세스 생성 성공만으로는 완료가 아닙니다. 인터페이스가 첫 데이터를 그린 뒤이거나 호출 이벤트를 받았을 때 확인하며, 런처는 10초를 기다리고 표시 확인에 2초를 더 줍니다. 핸드셰이크는 무작위 이름, 계정 ACL, 부모 프로세스 생성 시간과 고정 런처 경로를 사용합니다. 부모 프로세스가 종료된 뒤 도착한 늦은 요청은 창을 표시하지 않습니다. 단일 인스턴스는 여전히 기존 창을 표시하고 숨김으로 바꾸지 않으며, 시간 초과에도 기존 GoodGood을 종료하지 않습니다. 이번 요청만을 위해 만들어져 한 번도 표시되지 않은 인터페이스 인스턴스는 15초 뒤에 종료됩니다.

단일 인스턴스 인계는 표준 권한 프로세스가 이미 실행 중인 관리자 인스턴스에 접속하는 것을 지원합니다. 뮤텍스는 `SYNCHRONIZE`만 요청하고, 전용 메시지 창은 `WM_COPYDATA`만 UIPI를 통과시킵니다. 매개변수 길이, 형식과 핸드셰이크 신원은 여전히 검증합니다. 인계 프로세스는 0으로 종료한 뒤에도 원래 창의 확인을 계속 기다리고, 0이 아닌 종료는 즉시 종료 코드로 보고합니다. 인계에 실패한 핸드셰이크 프로세스는 이유를 기록하고 종료하며 자체 점검을 막는 대화 상자를 따로 띄우지 않습니다.

## 사용 설정과 복구 기록

1. 전용 설치 디렉터리를 잠그고 승인 계정과 기존 IFEO 구성을 확인합니다.
2. 더 이상 쓰지 않는 인터페이스 사본을 삭제하고 런처와 복구 프로그램을 준비합니다.
3. 관리자 유지 관리 보조 프로그램에서 무작위 이름의 창 없는 런처 사본을 만들어 일반 시작, 그리고 디버그 표시로 만들고 분리해 실행을 복원한 뒤의 정상 종료를 각각 확인합니다. 자체 점검은 임시 IFEO 항목을 만들거나 쓰지 않습니다. 무작위 프로그램에 대한 리디렉션 허가는 taskmgr.exe 수정 허가를 대신할 수 없습니다. 정리를 마치면 인터페이스 사본과 `taskmgr-recovery.txt` 비상 안내를 복사하고, 요청자의 표준 권한으로 인터페이스 준비 확인을 마칩니다. 시작이나 정리에 하나라도 실패하면 taskmgr.exe의 Debugger를 쓰지 않습니다. 자체 점검 실패와 정리 실패는 따로 보고하고 원본 오류를 유지합니다.
4. `taskmgr-recovery.json`의 Prepared 기록을 보호된 새 파일에 쓰고 동기화한 뒤 교체합니다. 기록에는 원래 값의 존재 여부, 종류와 원본 바이트, 이번에 쓴 값, 계정과 인터페이스 사본 이름이 들어갑니다. 첫 판은 기존 Debugger 인수를 거부하므로 유효한 원래 값은 존재하지 않습니다.
5. 현재 상태를 한 번 더 읽고 Debugger를 쓰고 레지스트리를 새로 고친 뒤 되읽어 검증하고, 마지막으로 기록을 Active로 바꿉니다.

복구는 현재 값이 이번에 쓴 값과 완전히 같은지 먼저 확인하고 Restoring을 기록한 뒤 원래 값을 복원하고 새로 고쳐 검증하며 마지막에 Restored를 기록합니다. 실제 상태가 이미 원래 상태이면 복구는 멱등입니다. 디렉터리 권한이 바뀌었거나 디렉터리가 없거나 복구 기록이 손상되었을 때, 명시적 복구 작업은 프로그램에 내장된 고정 런처 경로로 현재 `REG_SZ` 종류의 Debugger 값을 확인합니다. GoodGood 시작 명령과 완전히 일치할 때만 삭제하고 되읽어 확인합니다. 이 경로는 신뢰할 수 없는 기록의 명령을 읽지 않고 디렉터리 권한을 바꾸지도 않습니다. 다른 프로그램의 Debugger, UseFilter, 하위 키와 다른 값은 유지하며, 새로 만든 뒤 남은 빈 키는 Windows 시작 동작에 영향을 주지 않습니다.

레지스트리 값과 기록 파일은 단계별로 쓰고 Prepared / Restoring 기록으로 복구 절차를 이어 붙이므로, 어느 단계에서 전원이 끊겨도 다음 서비스 시작이나 복구 작업에서 복원을 계속할 수 있습니다. 설정 페이지는 디렉터리나 기록이 비정상일 때도 "Windows 작업 관리자 복구"를 제공하고 관리자 승인으로 실행합니다. 정상 유지 관리는 설치 잠금으로 직렬화하고, 독립 복구는 레지스트리를 직접 확인해 삭제 전후에 현재 값을 검증하며 다른 프로그램이 이미 넘겨받은 값은 그대로 둡니다.

복구 기록이 아직 Active이고 실제 구성이 저장된 원래 값으로 돌아갔으면 상태는 `revoked`("대체가 철회됨")이며, 한 번도 켜지 않았거나 명시적 복구를 마친 `disabled`와 구분합니다. 상태 조회는 읽기 전용을 유지하고 설정 페이지와 진단 요약이 철회 상태를 표시하며, 기록은 다음 명시적 사용 설정, 복구 또는 서비스 유지 관리까지 유지됩니다. 제3자 Debugger나 필터 구성은 여전히 충돌로 처리합니다. 서비스 시작과 상태 새로 고침 모두 이미 철회된 대체를 다시 쓰지 않습니다.

시작 자체 점검은 먼저 테스트 프로그램 이름을 독립 기록 `taskmgr-probe.txt`에 씁니다. 복구, 다음 자체 점검 또는 서비스 시작에서 중단된 임시 파일을 정리합니다. 구버전이 남긴 IFEO 항목이 있을 수 있는데, 이름이 기록과 같고 Debugger가 아직 구버전 자체 점검 값이며 필터 구성이 없을 때만 정리합니다. 다른 프로그램이 수정한 항목은 유지하고 오류로 보고합니다. 새 자체 점검은 파일만 만들고 구버전 항목이 없으면 레지스트리 삭제를 시도하지 않습니다. taskmgr.exe의 대체 값은 자체 점검 때문에 임시로 넣거나 빼지 않습니다.

레지스트리 접근은 작업별로 권한을 요청합니다. 상태 읽기는 값 조회와 하위 키 열거만 필요하고, 쓰기는 값 설정과 키 새로 고침에 필요한 조회 권한만 필요하며 알림 같은 무관한 권한은 요청하지 않습니다. 자체 점검 항목이나 taskmgr.exe 항목의 호출이 `ERROR_ACCESS_DENIED`로 거부되면 유지 관리 보조 프로그램이 `AccessCheck`로 현재 토큰과 그 호출이 실제로 요구하는 권한을 읽기 전용으로 확인합니다. 아직 없는 항목을 만들 때만 IFEO 상위 키의 하위 키 생성 권한을 검사합니다. DACL 검사를 통과해도 거부가 반드시 보호 소프트웨어 때문이라고 할 수는 없습니다. 핸들 권한, 토큰 제한, 무결성 수준, 시스템 정책과 레지스트리 필터가 모두 호출에 영향을 줄 수 있으므로 실패한 API, 오류 코드와 관련 기록을 함께 보고 판단해야 합니다. 검사가 통과하지 않았다는 것은 DACL이 검사한 접근 권한을 부여하지 않았다는 뜻일 뿐이며 권한을 누가 바꿨는지 추론하지 않습니다. GoodGood은 레지스트리 권한을 수정하거나 접근 제한을 우회하지 않습니다.

## 네이티브 대체 경로와 비상 복구

설정 페이지의 "시스템 작업 관리자 임시로 열기"는 로컬 명령 `open_native_task_manager`로 네이티브 시작 경로를 재사용해 현재 사용자 세션에서 Windows 기본 작업 관리자를 시작합니다. 작업은 백그라운드 스레드에서 실행되고 대체 구성과 복구 기록을 그대로 두며 권한 있는 서비스의 설치나 승인 상태와 무관합니다. 실패 정보는 설정 카드로 반환합니다.

네이티브 경로는 시스템 디렉터리의 고정 taskmgr.exe를 사용하고 IFEO에 붙은 임의 경로를 실행하거나 붙은 매개변수를 GoodGood에 전달하지 않습니다. 먼저 `DEBUG_ONLY_THIS_PROCESS | CREATE_SUSPENDED`로 만들고, 종료할 때 피디버깅 프로세스를 끝내지 않도록 설정한 뒤 디버깅에서 분리하고 스레드를 다시 시작해 IFEO로 다시 들어가지 않게 합니다. 분리에 실패하면 이번에 만든 프로세스를 정리하고 오류로 보고하며 다른 프로세스는 끝내지 않습니다. API 동작은 [DebugActiveProcessStop](https://learn.microsoft.com/en-us/windows/win32/api/debugapi/nf-debugapi-debugactiveprocessstop)과 [DebugSetProcessKillOnExit](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-debugsetprocesskillonexit)을 참조하십시오.

이 경로는 서비스와 GoodGood 인터페이스와 무관합니다. 시스템 정책, 토큰 제한이나 파일 손상으로 네이티브 시작이 실패하면 런처가 오류를 안내합니다. 런처 자체가 손상되었거나 삭제되었으면 비상 안내에 따라 복구해야 합니다.

독립 복구 프로그램은 보호된 디렉터리의 `goodgood-taskmgr-recover.exe`이고 직접 실행하면 관리자 권한을 요청하며 GoodGood 인터페이스나 서비스를 필요로 하지 않습니다. 이 프로그램도 손상되었으면 Win+R로 관리자 레지스트리 편집기를 열어 Debugger가 실제로 이 설치의 런처를 가리키고 신뢰할 수 있는 복구 기록의 원래 값이 존재하지 않음을 확인한 뒤 그 Debugger 값만 삭제할 수 있습니다. 이미 있는 제3자 값은 삭제해서는 안 되고, 백업이 없으면 먼저 귀속을 직접 확인해야 합니다.

## 업데이트와 제거

권한 있는 서비스를 제거하기 전에 GoodGood이 쓴 작업 관리자 대체를 먼저 철회해야 하며 다른 프로그램의 구성은 그대로 둡니다. 제거 검사는 현재 설치된 `goodgood.exe`가 수행하고, 디렉터리나 복구 기록이 비정상이면 독립 복구 경로를 사용하며, 레지스트리 삭제나 검증에 실패하면 제거를 중지합니다. 서비스를 업데이트할 때 복구 기록이 Active이고 Debugger가 GoodGood이 쓴 값과 같으며 필터가 설정되지 않았으면 인터페이스 사본을 먼저 갱신하고 그다음 서비스를 갱신해 켜 둔 대체와 IFEO 구성을 유지합니다. 완료되지 않은 다른 상태는 먼저 복구를 수행하고, 제3자 충돌, 기록 손상이나 쓰기 실패에서는 업데이트를 중단합니다. 기록이 이미 Restored이면 이번 대체는 복원된 것이므로 이후 나타난 제3자 Debugger, UseFilter와 하위 키는 해당 도구가 관리합니다.

설치 프로그램이 GoodGood을 업데이트할 때는 새로 설치된 `goodgood.exe --goodgood-close-copies`가 실행 중인 작업 관리자 대체 인터페이스 사본을 먼저 끝내고, 같은 방식으로 서비스를 갱신합니다(설치 후 훅, [권한 있는 서비스](privileged-service.md) 참조). 서비스가 제거되었더라도 이 사본들을 닫아 업그레이드 후 시작이 구버전으로 넘어가지 않게 합니다. 대체를 새 버전에 맞추는 순서는 다음과 같습니다. 먼저 업데이트를 시작한 `goodgood.exe`(설치 프로그램이 업데이트할 때는 새로 설치된 프로그램)를 새 이름의 인터페이스 사본으로 복사하고, 런처와 복구 프로그램을 제자리에서 교체한 뒤, 복구 기록이 새 사본을 가리키게 하고, 마지막으로 비상 안내를 갱신하고 옛 사본을 삭제합니다. IFEO 값은 런처만 가리키므로 바뀌지 않아 시스템 진입점을 수정하지 않고 자체 점검을 다시 하지도 않습니다. 인터페이스 사본이 실행 중이면 교체도 삭제도 할 수 없으므로 새 버전은 새 이름을 쓰고, 옛 사본은 종료된 뒤 다음 정리에서 삭제합니다. 런처가 실행 중이면 교체가 실패하므로 이번 새 사본을 함께 삭제하고 기록과 원래 사본은 그대로 두며 서비스도 갱신하지 않고 잠시 후 다시 시도하거나 먼저 복구한 뒤 업데이트하도록 안내합니다. 이 단계는 인터페이스 준비 검사를 다시 하지 않으며, 새 버전 인터페이스가 준비되지 않으면 런처가 평소처럼 Windows 작업 관리자를 열도록 바꾸고 이유를 `taskmgr.log`에 기록합니다. 대체가 꺼져 있거나 아직 완료되지 않았거나 다른 프로그램이 다시 쓴 상태면 이 단계는 아무것도 바꾸지 않고 앞 단락대로 처리합니다.

포터블 프로그램을 직접 교체하거나 설치할 때 서비스 업데이트에 실패하면 Ctrl+Shift+Esc는 계속 기존 사본을 엽니다. 설정은 주, 부, 수정 버전을 비교해 사본을 판단하고 "서비스 업데이트"를 안내합니다. 직접 업데이트한 뒤에는 트레이에서 아직 실행 중인 옛 인스턴스를 종료해 다음 시작이 새 사본을 쓰게 합니다.

[`installer-hooks.nsh`](../../packaging/windows/installer-hooks.nsh)는 제거 전에 `goodgood.exe --goodgood-close-copies`를 호출해 인터페이스 사본을 해제하고 관리자 권한 시작 승인을 철회한 뒤, 권한 있는 서비스도 함께 제거할지 묻습니다. 이어서 현재 설치된 `goodgood.exe --goodgood-taskmgr-uninstall`을 호출해 복구 검사를 수행하므로 구버전이나 권한이 비정상인 디렉터리의 복구 프로그램을 실행하지 않습니다. 승인을 취소하거나 복구에 실패하면 제거를 중지합니다. 훅은 업그레이드 중의 제자리 제거를 인식해 서비스 디렉터리의 대체 파일을 유지합니다. 정리는 이미 종료된 인터페이스 사본만 다루고 복구 프로그램과 백업은 유지합니다.

## 코드와 검증

[`crates/goodgood-service/src/taskmgr/`](../../crates/goodgood-service/src/taskmgr)에는 상태 기계, 레지스트리 어댑터, 자체 점검, 시작과 토큰 처리 및 인터페이스 핸드셰이크가 있습니다. 릴리스 빌드는 두 개의 `goodgood-taskmgr-*` 보조 프로그램을 먼저 컴파일한 뒤 GoodGood에 포함합니다. 대체 진입점은 릴리스 빌드에서만 열립니다.

서비스 프로토콜 4판은 매개변수가 없는 `RestoreTaskManager`만 추가하며 범용 레지스트리 쓰기, 임의 명령이나 경로 인터페이스는 없습니다. 사용 설정은 여전히 명시적 승인을 받는 관리자 유지 관리 보조 프로그램으로 진행합니다. 복구에 실패하면 독립 보조 프로그램이 다시 검증한 뒤 재시도할 수 있고, 이 복구 동작은 기록에 따라 멱등입니다.

일반 테스트는 메모리 레지스트리와 직접 만든 하위 프로세스로 백업 실패, 제출 실패 시 되돌리기, 중단된 단계의 복구, 반복 복구, 제3자 충돌, 필터 키 거부, 복구 실패 시 기록 유지, 복구 후 나타난 제3자 값이 서비스 유지 관리를 막지 않음, 서비스를 업데이트할 때 어떤 상태에서 대체를 새 버전에 맞추고 유지하는지, 대체 파일 갱신 순서와 실패 시 되돌리기, 명령줄 이스케이프, 실제 디버그 생성 후 분리와 실행 종료, 그리고 부모 프로세스를 지정할 때의 토큰 상속(중간 무결성 생성자가 낮은 무결성 부모를 지정하면 하위 프로세스가 부모의 낮은 무결성을 상속)을 검증합니다. 시작 자체 점검은 일반 시작과 디버그 시작 실패, 레지스트리 쓰기 권한이 없어도 런처를 검사할 수 있음, 임시 파일 정리, 구버전 IFEO 항목 정리와 제3자 구성 유지를 다룹니다. 릴리스 런처는 표준 권한에서 두 가지 시작 방식을 따로 검증합니다. 레지스트리 키 권한 판단은 HKCU의 임시 키로 검증하고 끝난 뒤 삭제합니다. 테스트는 실제 IFEO를 쓰지 않고 시스템 작업 관리자를 실행하지도 않습니다.

유지 관리 보조 프로그램에 오류가 생기면 실패한 단계, 안내 문구, 오류 분류와 레지스트리 호출 정보를 서비스 디렉터리의 `taskmgr-error.json`에 기록합니다. 작업을 시작한 인터페이스가 이를 되읽어 설정 페이지에 안내 문구를 표시하고, 진단 로그에는 고정된 단계 이름, 오류 분류, API 이름, 접근 마스크, Windows 오류 코드와 DACL 검사 결과만 기록하며 안내 문구나 경로는 기록하지 않습니다. 자체 점검과 정리가 함께 실패하면 두 번의 실패 호출과 권한 검사 결과를 각각 유지해 정리 오류가 원래 오류를 덮지 않게 합니다. 보조 프로그램은 실행할 때마다 이전 기록(0.1.0의 `taskmgr-error.txt` 포함)을 먼저 지우고, 쓸 수 없을 때만 메시지 상자를 띄웁니다. 런처에는 창이 없으므로 GoodGood을 열지 못해 Windows 작업 관리자를 열도록 바뀌었을 때나 사용 설정 중 인터페이스 자체 점검이 실패했을 때 현재 계정의 로그 폴더에 있는 `taskmgr.log`에 이유를 덧붙입니다(256 KB를 넘으면 새로 시작).

`taskmgr.log`에는 초기 단일 인스턴스 인계의 실패 API, HRESULT, 양쪽 무결성 수준과 소요 시간, 그리고 인터페이스 핸드셰이크의 구체적 단계, 런처 권한, 하위 프로세스 실행 여부와 종료 코드도 기록합니다. 받는 쪽이 부모 프로세스, 런처 이미지나 이벤트 검증에 실패하면 해당 검사를 기록합니다. 프로세스 경로, 계정 이름이나 시작 매개변수는 기록하지 않습니다.
