# 권한 있는 서비스

`crates/goodgood-service`는 선택적인 Windows 서비스를 제공하며 LocalSystem으로 백그라운드에서 실행됩니다. 승인된 프로세스 작업, 자동 규칙, 서비스 제어와 IPv4 TCP 연결 끊기 요청을 수행하고, 필요할 때 핸들, 프로세스별 네트워크 및 디스크 카운트와 커널 센서 값을 조회합니다. 설정 진입점은 [권한](../guide/settings.md)을 참조하십시오.

## 모듈

| 모듈 | 역할 |
|---|---|
| `lib.rs` | 서비스와 설치 보조 프로그램 시작 분기, 호스트 호출 진입점, 개발 버전과 릴리스 버전 격리 |
| `install.rs` | SCM 상태 조회, UAC 설치 보조 프로그램, 보호된 사본, 설치·업데이트·시작·제거와 업데이트 실패 시 되돌리기 |
| `server.rs` | SCM 진입점, 실행·중지 상태, 중지 이벤트와 종료 정리 |
| `pipe.rs` | 로컬 명명된 파이프, 길이가 제한된 메시지, 연결 신원 검증, 비동기 I/O와 취소 |
| `snapshot.rs` | 주기 스냅숏의 통합 새로 고침, 유효 기간이 있는 캐시와 유휴 임대. 데이터 종류마다 콜드 읽기 대기자는 하나이며 파이프 처리 능력을 유지합니다 |
| `protocol.rs` | 버전이 있는 작업 허용 목록, 매개변수 검증과 `goodgood-core` 호출 |
| `security.rs` | SID, 파이프 ACL, 호출자 토큰, 파일 및 디렉터리 권한 검사 |
| `cleanup.rs` | 권한 철회 후 파일 정리: 각 단계 디렉터리 고정, 디렉터리 링크 거부, 알려진 파일만 삭제, 코드 실행 권한을 부여하지 않음 |
| `network.rs` | 서비스 측 ETW 임대, 누적 바이트 수, 카운트 출처와 세대 |
| `disk.rs` | 서비스 측 전체 프로세스 정보 디스크 스냅숏(PID, 생성 시간과 누적 바이트 수만 포함). 호스트 측 디스크 읽기 스레드는 최신 스냅숏만 샘플링 스레드에 넘겨 속도를 환산합니다 |
| `sensors/` | 서비스 측 PawnIO 모듈, 고정 CPU 레지스터 구성, 온도와 전력 환산. 호스트의 비동기 읽기와 만료 캐시 정리 |
| `driver/` | 커널 센서를 직접 켤 때의 드라이버 준비: 고정 설치 패키지, 다운로드와 서명 검증, 독립 UAC 보조 프로그램, SCM 신원과 실행 상태 확인 |
| `background.rs` | 호스트 측 규칙 스레드와 네트워크 읽기 스레드. 최신 결과만 샘플링 스레드에 넘깁니다 |
| `handles.rs` | 핸들 조회 보조 프로세스의 시작, Job 관리, 시간 초과 시 이어 찾기, 부분 결과 회수와 로컬 대체 |
| `taskmgr/` | 시스템 작업 관리자 대체, 복구 상태 기계, 독립 런처와 인터페이스 준비 핸드셰이크 |

## 설치와 권한 부여

서비스 이름은 `GoodGoodPrivileged`이고 개발 버전은 `GoodGoodPrivilegedDev`입니다. 호스트는 설정 페이지의 명시적 조작이 있을 때만 `ShellExecuteExW`의 `runas`로 관리자 권한을 요청하며, UAC를 취소해도 인터페이스를 종료하지 않고 서비스를 바꾸지도 않습니다. 보조 프로그램은 네이티브 창과 단일 인스턴스 처리보다 먼저 매개변수를 처리해 이미 실행 중인 인터페이스에 인수가 삼켜지지 않게 합니다.

보조 프로그램은 자신의 프로그램을 시스템이 알려진 폴더인 Program Files 아래 `GoodGood Privileged`(개발 버전은 `GoodGood Privileged Dev`)로 복사하고, 따옴표로 감싼 절대 경로로 자동 시작하는 LocalSystem 서비스를 등록합니다. 디렉터리, 실행 파일과 `owner.sid`의 소유자는 Administrators이고 Administrators와 SYSTEM만 쓸 수 있습니다. 디렉터리 재분석 지점, 신뢰할 수 없는 소유자와 다른 계정의 쓰기 권한을 거부합니다. 설치 디렉터리나 포터블 버전이 있는 위치에 의존하지 않으며, 복사는 기존 파일을 덮어쓰지 않습니다.

보호된 경로와 레지스트리의 소유자, 쓰기 ACE는 고정 SID로 검증하고 SYSTEM, Administrators와 TrustedInstaller만 신뢰합니다. Program Files의 TrustedInstaller 소유자는 Windows Resource Protection의 [고정 SID](https://learn.microsoft.com/en-us/archive/msdn-magazine/2008/november/access-control-understanding-windows-file-and-registry-permissions) `S-1-5-80-956008885-3418522649-1831038044-1853292631-2271478464`를 사용합니다. 검증은 SID를 직접 비교하므로 계정 이름 조회를 쓸 수 없어도 이 소유자를 식별할 수 있습니다. 다른 서비스 계정이나 일반 사용자를 소유자로 두거나 그런 계정에 유효한 쓰기 권한을 부여한 경우, 그리고 NULL DACL은 모두 거부합니다. 관리자 권한 시작의 보호된 디렉터리도 같은 검증을 공유합니다.

복사 원본은 권한 상승 상태로 실행 중인 `goodgood.exe` 자체이고, 대상 디렉터리의 쓰기 권한 보호는 복사 후에 적용됩니다. 설치 버전은 Program Files에 있어 관리자만 쓸 수 있으므로 원본을 신뢰할 수 있습니다. 포터블 버전을 표준 사용자가 쓸 수 있는 폴더에 두면 로컬 악성 프로그램이 승인 전에 이를 교체할 수 있고, 교체된 프로그램은 관리자 권한으로 실행되어 SYSTEM 서비스로 등록됩니다. 이는 알려졌고 받아들인 위험입니다(포터블 버전은 원본을 검증하지 않음). 사용자 문서는 설치 버전을 쓰거나 포터블 버전을 관리자만 쓸 수 있는 위치에 두도록 안내합니다.

`owner.sid`는 설치할 때 인터페이스 프로세스의 Windows 계정을 기록하며, UAC에서 다른 관리자의 자격 증명을 입력해도 승인 대상은 바뀌지 않습니다. 서비스는 계정과 토큰으로 호출자를 검증합니다. 같은 계정의 다른 중간 이상 무결성 수준 로컬 프로그램도 고정된 관리 작업을 계속 호출할 수 있습니다. 이 작업들은 그 자체로 컴퓨터 전체에 작용합니다. 중요하지 않은 임의 프로세스를 끝내거나 일시 중단·재개하고, 임의 프로세스의 우선 순위, I/O 우선 순위와 메모리 우선 순위를 바꾸고, 임의 서비스를 시작·중지하고 시작 유형을 바꾸며(GoodGood 자체 서비스만 보호), 임의의 IPv4 TCP 연결을 끊고, SYSTEM 신원으로 파일 잠금을 조회합니다. 따라서 권한 부여는 그 계정에 일부 관리자 능력을 주는 것과 같으며, 인터페이스의 설치 확인 상자가 항목별로 이를 나열합니다. 이를 통해 임의 프로그램을 실행하거나 임의 파일을 쓰고, 서비스 실행 경로를 바꾸거나 드라이버를 로드할 수는 없습니다. 다른 계정, 낮은 무결성 프로세스, 그리고 제한된 토큰과 AppContainer 토큰(같은 계정의 샌드박스 프로세스)은 모두 거부합니다. 승인 대상은 사용자 계정 SID(`S-1-5-21-…` 또는 Microsoft Entra의 `S-1-12-1-…`)만 될 수 있고 그룹과 기본 제공 SID는 받지 않습니다.

업데이트는 새 사본을 먼저 만든 뒤 서비스를 중지하고 SCM 경로를 바꿉니다. 구성이나 시작에 실패하면 이전 경로와 원래 실행 상태로 되돌리려 시도합니다. 중지할 때는 SCM의 중지 상태와 서비스 프로세스 종료를 모두 기다려 아직 매핑된 실행 파일을 삭제하지 않습니다. SCM이 어떤 사본도 더 이상 참조하지 않음을 확인한 뒤에만 정리합니다. 제거는 같은 이름의 서비스가 실제로 GoodGood 전용 디렉터리를 가리키는지 확인하고 서비스를 중지·삭제한 뒤 알려진 파일을 삭제하며, 디렉터리를 재귀적으로 삭제하지 않습니다. 실패하면 아직 참조되는 사본을 유지합니다.

디렉터리 권한이 바뀌면 상태 조회는 "사용할 수 없음"과 오류 원인을 반환하고 제거 진입점은 유지합니다. 제거는 SCM의 고정 서비스 이름, 서비스 종류, 계정과 프로그램 경로로 소유를 확인하고, 작업 관리자를 복구한 뒤 서비스를 중지·삭제하고 독립 정리 경로로 알려진 파일을 삭제합니다. 설치, 업데이트, 시작과 서비스 연결은 계속 소유자와 ACL을 검증합니다. 권한 철회는 시스템 디렉터리 권한을 바꾸지 않고 손상된 실행 디렉터리의 프로그램을 실행하지도 않습니다. 제거 훅은 항상 현재 설치된 `goodgood.exe`를 호출해 복구 검사를 수행합니다.

서비스와 GUI는 따로 설치됩니다. 설치 프로그램의 설치 후 훅이 서비스의 레지스트리 항목을 발견하면 설치 프로그램이 이미 가진 관리자 권한으로 `goodgood.exe --goodgood-service-refresh`를 실행해 서비스를 갱신하며, 승인 대상 계정은 서비스 디렉터리의 `owner.sid`에 기록된 계정을 씁니다. 실패해도 설치에 영향을 주지 않습니다. 이 단계는 설정 페이지의 "서비스 업데이트"와 같은 보조 프로그램을 씁니다. 작업 관리자 대체가 켜져 있으면 대체에 쓰는 런처, 복구 프로그램과 인터페이스 사본을 먼저 새 버전으로 갱신하고 IFEO 값은 바꾸지 않아 대체를 켠 채로 두며, 그다음 서비스를 갱신합니다. 자세한 내용은 [시스템 작업 관리자 대체](task-manager.md#업데이트와-제거)를 참조하십시오. 업데이트에 실패하면 GUI가 처음 시작할 때 서비스 버전 불일치를 발견해 서비스 업데이트 여부를 묻습니다. GUI를 제거할 때 NSIS 제거 프로그램은 서비스의 레지스트리 항목을 발견하면 함께 제거할지 묻고, 동의하면 `goodgood.exe --goodgood-service-remove`로 설정 페이지와 같은 UAC 보조 프로그램을 실행합니다(작업 관리자를 먼저 복구). 승인을 취소하거나 실패하면 사용자가 GUI 제거를 계속할지 중지할지 선택합니다. 업그레이드 설치의 "먼저 제거 후 설치" 방식인 제자리 제거는 이 단계를 실행하지 않습니다.

## IPC 경계

- 파이프는 `\\.\pipe\GoodGood.Privileged.v1`이고 개발 버전은 `\\.\pipe\GoodGood.Privileged.Dev.v1`이며 원격 연결을 거부합니다. 첫 인스턴스가 독점적으로 만들고, 다음 수신 인스턴스는 현재 연결을 넘기기 전에 만들어 파이프 이름을 빼앗기지 않게 합니다.
- 클라이언트가 접속 전에 끊으면 서비스는 연결을 끊고 현재 수신 인스턴스를 재사용해 이후 요청을 계속 처리합니다. 접속 시점의 파이프 닫힘 오류(109, 232, 233)는 한 번의 연결 종료로 처리합니다. 연결 수가 상한에 이르러도 수신 인스턴스를 재사용해 파이프 이름 점유와 인스턴스 수 상한을 유지합니다.
- 파이프는 작업 스레드 8개를 재사용하고 스레드 로컬 및 DLL 정리는 서비스가 중지될 때 한꺼번에 마칩니다. 수신 스레드는 이미 응답한 요청의 스레드 종료를 기다리지 않습니다. 연결 슬롯은 서버 측 파이프 핸들이 닫힌 뒤 반환되고, 대기 및 처리 중 요청의 합계도 여전히 8개를 넘지 않습니다.
- ACL은 SYSTEM, 권한 상승한 Administrators와 승인 계정에만 접근을 허용합니다. 승인 계정은 데이터 읽기·쓰기, 속성 읽기와 동기화 권한만 받고 `FILE_CREATE_PIPE_INSTANCE`는 받지 않습니다. 이유는 Microsoft의 [명명된 파이프 접근 권한 설명](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights)을 참조하십시오.
- 클라이언트는 SCM의 서비스 PID로 파이프 서버 PID를 확인하고 프로세스 동기화 핸들을 보유해 PID 재사용을 막습니다. 서비스는 승인 계정에만 자신의 프로세스 조회와 동기화 권한을 엽니다. 클라이언트는 식별 수준으로 제한되어 파이프 서버가 이를 빌려 작업을 실행할 수 없습니다.
- 서비스는 파이프에서 호출자를 가장해 실제 토큰의 계정 SID와 무결성 수준을 검증한 뒤 자신의 신원을 복원합니다. 복원에 실패하면 서비스를 종료합니다.
- 프로토콜은 12판이며 I/O와 메모리 우선 순위 작업을 포함합니다. 파이프 이름과 1판 Ping 봉투는 구버전 서비스를 발견해 업데이트를 안내하기 위해 유지합니다. 그 밖의 요청은 버전 불일치, 알 수 없는 작업과 알 수 없는 필드를 거부합니다. 요청 상한은 16 KiB, 응답 상한은 1 MiB로 유지해 네트워크 누적 카운트와 핸들 결과를 담습니다. 동시에 최대 8개 요청을 처리합니다. 읽기 제한 시간은 5초, 수동 작업 요청은 30초, 백그라운드 규칙·네트워크·디스크·센서 요청은 2초, 핸들 요청은 20초입니다(연결 대기는 1초 추가). I/O를 취소한 뒤에는 완료를 기다렸다가 버퍼를 해제합니다.
- 네트워크, 디스크와 센서의 네이티브 읽기는 각각 작업 스레드 하나에서 실행됩니다. 유효한 캐시는 즉시 반환하고, 캐시가 만료되었거나 없으면 데이터 종류마다 요청 하나만 새 샘플을 기다리게 하며 최대 1.5초입니다. 다른 요청은 즉시 대기 상태나 빈 스냅숏을 받습니다. 동시 요청은 한 번의 새로 고침으로 합쳐지고 네트워크와 디스크는 최소 250 ms, 센서는 최소 500 ms 간격입니다. 네트워크와 디스크 캐시의 유효 기간은 2초, 센서는 3초이며 읽기가 캐시 유효 기간을 늘리지는 않습니다. 15초 동안 요청이 없으면 데이터 원본과 캐시를 해제하고, 그동안에는 요청에 따라서만 새로 고치며 백그라운드 저빈도 샘플링은 원래 주기를 유지합니다. 네트워크 누적 카운트와 디스크 카운트는 실제 수집 시각을 유지하고 같은 프레임을 다시 읽으면 기존 속도를 그대로 씁니다.
- 프로세스 작업은 PID와 양수 시작 시간을 모두 제공해야 하며 `actions::open_instance`의 검증을 따릅니다. 프로세스 끝내기는 시스템 중요 프로세스 검사를 우회하는 `force` 매개변수를 받지 않고, 클라이언트가 자기 자신이나 서비스를 끝내는 것도 허용하지 않습니다. 일시 중단과 다시 시작(`Suspend`)도 PID 0과 4, 서비스 자신과 요청한 클라이언트를 거부하며, 일시 중단에서는 시스템 중요 프로세스, `dwm.exe`와 권한 있는 서비스 프로세스도 거부하고, Windows가 동결한 프로세스는 양방향 모두 거부합니다. 다시 시작은 일시 중단 한 번만 되돌리므로 다른 도구가 여러 번 겹쳐 중단한 프로세스는 여러 번 다시 시작해야 합니다. I/O 우선 순위(`IoPriority`)는 매우 낮음, 낮음과 보통만 받고 높음과 중요는 Windows가 예약해 둡니다. 메모리 우선 순위(`MemoryPriority`)는 1부터 5까지 다섯 단계를 받습니다. 서비스 제어로 GoodGood 권한 있는 서비스 자체를 중지하거나 바꿀 수도 없습니다.
- 끝내기 작업은 신원을 확인한 같은 프로세스 핸들에서 `IsProcessCritical`을 호출하며 `PROCESS_QUERY_LIMITED_INFORMATION`만 있으면 됩니다. 검사에 실패하면 `criticalityUnknown`을 반환하고 끝내지 않으며, 그룹 작업, 프로세스 트리와 설치 정리 경로도 안전성을 확인할 수 없는 대상을 건너뜁니다. 구버전 프로토콜 서비스는 작업 전에 요청을 거부하고, 호스트는 기존 호환 절차대로 로컬 권한으로 바꿔 구버전 검사 로직이 새 보호를 우회하지 않게 합니다.
- 프로세스 작업, 규칙과 서비스 제어를 보낸 뒤 응답을 잃으면 실행 결과를 알 수 없으므로 호스트는 재전송을 금지합니다. Ping이 아닌 요청의 프로토콜 버전이 맞지 않으면 서비스는 실행 전에 거부하고 파이프를 닫아야 합니다. 호스트는 원래 서비스 프로세스 핸들을 보유하고 1판 봉투로 Ping을 다시 보내 상대가 구버전 프로토콜을 쓰는지 확인한 뒤에야 로컬 권한으로 실행합니다. 권한이 부족하면 `ActionError::ServiceOutdated`를 반환하고 "서비스 업데이트"를 안내합니다. 규칙도 그 서비스 프로세스가 종료되기 전까지는 로컬 실행으로 바뀝니다. 주기 수집, 읽기 전용 핸들 조회와 멱등성 있는 작업 관리자 복구는 아래에서 따로 다룹니다. `pipe.rs`는 하위 프로세스로 잘못된 버전 요청의 거부 동작을 검증합니다.

## 디스크 세부 정보

`DiskDetails { index }`는 0–4095의 물리 디스크 번호만 받고 서비스가 `PhysicalDrive` 경로를 이어 붙입니다. 요청은 경로, IOCTL, 명령 바이트나 쓰기 데이터를 받지 않습니다. 서비스는 고정된 ATA IDENTIFY, SMART READ DATA/READ THRESHOLDS/RETURN STATUS, SAT 16/12바이트 읽기 전용 명령과 SCSI VPD 80h 및 LOG SENSE 상태·온도·오류 카운트 조회만 보냅니다. 읽기는 SMART 사용 설정 상태를 유지하고 자가 검사를 실행하지 않으며 매체나 펌웨어를 바꾸지 않습니다.

디스크 세부 정보는 세부 정보 페이지를 열거나 직접 새로 고칠 때만 읽고, pass-through 명령 하나의 제한 시간은 2초이며 20초 예산을 다 쓰면 이후 명령을 보내지 않습니다. 같은 서비스는 디스크 세부 정보 조회를 한 번에 하나만 실행하고 다른 요청은 즉시 거부합니다. 확장에 실패하면 일반 속성과 각 조회 상태를 유지합니다. 호스트는 이미 실행 중인 서비스에만 연결하고, 서비스가 없거나 프로토콜이 오래되면 일반 권한 결과를 유지하고 이유를 표시합니다. 인터페이스 필드는 [디스크 세부 정보 인터페이스](core.md#디스크-세부-정보-인터페이스)를 참조하십시오.

## 시스템 작업 관리자 대체

시스템 작업 관리자 대체는 서비스로만 고정된 복구 작업을 제공하고, 켜는 일은 관리자 유지 관리 보조 프로그램이 맡습니다. 업데이트와 제거는 시스템 진입점을 먼저 복구합니다. 상태 기계, 독립 프로그램과 검증 경계는 [시스템 작업 관리자 대체](task-manager.md)를 참조하십시오.

## 핸들 조회

`FindHandles`는 읽기 전용 요청이며 서비스의 계정과 무결성 수준 검증을 사용합니다. 서비스를 쓸 수 없거나 조회에 실패하면 호스트가 현재 계정 권한으로 다시 시도하고 서비스 오류를 보관합니다. 프로토콜 버전이 오래되면 설정에서 서비스를 업데이트할 수 있습니다.

매 스캔은 자신의 프로그램을 보조 모드로 시작하며, 네이티브 창, 단일 인스턴스와 샘플러 초기화보다 먼저 분기합니다. 하위 프로세스는 시작 바이트 하나를 기다리고, 부모 프로세스가 닫히면 종료되는 Job에 넣은 뒤에야 진행시킵니다. Job은 프로세스 하나와 전용 메모리 256 MiB로 제한합니다. 하위 프로세스는 창을 만들지 않고 작업 디렉터리를 시스템 디렉터리로 고정해 스스로 조회 대상 디렉터리를 점유하지 않게 합니다.

`goodgood-core::handles`는 `NtQuerySystemInformation(SystemExtendedHandleInformation)`으로 핸들 표를 읽고, 자신이 가진 NUL 핸들로 File 종류 인덱스를 동적으로 식별합니다. 구조 레이아웃은 [phnt](https://github.com/winsiderss/phnt/blob/master/ntexapi.h)를 참고하며, 읽기 전에 반환 길이와 항목 수를 확인합니다. 원본 프로세스를 연 뒤 생성 시간을 확인하고 `DuplicateHandle`로 핸들을 복제합니다. 종류를 다시 확인하고 파이프와 장치를 제외한 뒤 `NtQueryObject`로 이름을 읽습니다. 복제본만 닫고 원본 핸들은 닫지 않습니다.

파일은 볼륨 번호와 파일 ID를 먼저 비교해 하드 링크를 식별하고, 파일 ID가 없으면 이름 일치로 물러납니다. 디렉터리는 경로 구분자 경계로 자신과 하위 항목을 맞추므로 `folder-other`를 `folder`로 세지 않습니다. 결과에는 PID, 시작 시간, 프로세스 이름, 첫 일치 경로와 핸들 수가 들어가며, Restart Manager의 결과는 로드된 모듈 같은 참조를 보충하는 데 계속 쓰입니다.

복제, 이름 조회, 파일 정보와 핸들 닫기는 모두 보조 프로세스에서 수행합니다. 보조 프로세스는 조회 전에 진행 커서를 보내고 일치 항목을 하나씩 반환하며, 부모 프로세스는 `PeekNamedPipe`로 이미 있는 바이트를 읽어 영구히 막힐 수 있는 읽기 스레드를 따로 만들지 않습니다. 커서 하나가 500 ms 동안 진행이 없으면 보조 프로세스를 끝내고, 발견한 항목을 유지한 채 커서 다음부터 다시 시작하며 재시작은 최대 4회입니다. 준비 단계는 3초, 컨트롤러 전체 예산은 15초이고 보조 프로세스 자체에도 12초 예산이 있습니다. 시간 초과나 조기 종료 모두 이미 찾은 결과를 반환하며, 프로세스 생성과 자원 정리 시간은 따로 계산합니다.

부모 프로세스마다 핸들 스캔은 한 번에 하나만 실행합니다. 조회하거나 건너뛸 후보는 최대 200,000개, 반환 프로세스는 128개이며 긴 이름과 경로는 잘라서 표시합니다. 네트워크, 장치, 상대 경로, 데이터 스트림과 경로 탈출을 거부하고, 대상은 `\Device\HarddiskVolume…`으로만 매핑하며 `OBJ_DONT_REPARSE`로 열어 SYSTEM이 디렉터리 연결로 원격 공유에 끌려가지 않게 합니다. 링크 대상은 따로 선택할 수 있고, 인터페이스는 Restart Manager의 결과와 한계 설명을 그대로 유지합니다.

스캔은 조회 시점의 파일 참조를 반영하고 삭제 공유를 허용한 핸들도 나열합니다. 보호된 프로세스, 권한 부족, 닫히거나 재사용 중인 핸들, 매핑만 남은 파일 때문에 결과가 불완전할 수 있습니다. 인터페이스는 PID와 시작 시간으로 출처를 합치고, 프로세스를 끝낼 때도 조회할 때의 인스턴스 정보를 계속 사용합니다.

## 자동 규칙과 네트워크 샘플링

호스트의 `RuleRunner` 스레드는 PID, 시작 시간과 이름으로 규칙을 맞춥니다. 스레드가 바쁘면 최신 스냅숏만 유지하고 RPC는 구성과 통계 잠금을 해제한 뒤 실행합니다. 규칙을 수정하면 이미 보낸 작업은 완료될 수 있고, 보내지 않은 이전 작업과 이전 버전 통계는 함께 버려집니다.

일치 항목마다 `ApplyRule` 요청 하나를 써서 효율성 모드를 먼저 설정하고 명시적 우선 순위를 다음에 설정하며 두 단계 모두 프로세스 인스턴스를 검증합니다. 전송이 한 번 실패하면 이번 묶음의 나머지 대상도 실패로 기록하고 같은 서비스의 시간 초과를 더 기다리지 않으며, 확실하지 않은 작업을 자동으로 재전송하지 않습니다. 다음 규칙 저장이나 서비스 PID/가용 상태 변화 때 기존 프로세스를 다시 확인하고 이전 통계를 비웁니다.

서비스가 `NetworkSnapshot`을 처음 받으면 자체 ETW 세션을 시작합니다. 릴리스 버전 이름은 `GoodGood Service Network`, 개발 버전은 `GoodGood Service Network (dev)`입니다. 시작할 때 같은 이름의 남은 세션을 정리하고, 15초 동안 읽기가 없으면 세션을 닫으며, 종료할 때 소비자 스레드가 끝나기를 기다립니다. ETW 시작에 실패하거나 소비자가 종료되면 사용할 수 없음으로 반환하고 최소 30초 간격으로 다시 시도합니다.

네트워크 응답에는 출처 epoch, 출처 시계(마이크로초), 최대 8192개 PID의 누적 송수신 바이트와 카운트 세대가 들어갑니다. 서비스의 네트워크 스레드만 tracker에서 원본 증분을 가져가고, 서로 다른 클라이언트가 같은 누적 카운트를 읽어 데이터를 서로 소비하지 않습니다. 30초 동안 활동이 없는 항목은 회수되고 다시 나타나면 새 세대를 받습니다. 용량을 넘거나 카운트가 넘치면 그 출처를 닫고 사용할 수 없음으로 반환합니다.

호스트의 `NetworkClient`는 실행할 읽기 하나와 완료 결과 하나만 유지합니다. 로컬 ETW를 쓸 수 있으면 로컬 결과를 우선 사용하고, 아니면 샘플링 스레드가 백그라운드 캐시를 읽어 출처 시계로 속도를 계산한 뒤 인터페이스와 기록에 넘깁니다. 출처가 바뀌거나 PID 시작 시간 변화를 관찰하면 기준선을 다시 세우고, 같은 스냅숏을 다시 읽어도 바이트를 두 번 계산하지 않습니다. 백그라운드 통신과 서비스 캐시 때문에 샘플링 지연이 생기므로 속도는 실제 출처 시각을 유지하며, 호스트 캐시는 두 샘플링 간격(이번과 지난 샘플링 중 긴 주기)에 2초를 더한 시간을 넘으면 무효가 됩니다. 서비스 연결이 끊겨 빈 결과를 받으면 네트워크 열을 숨기고, 복구 후 첫 데이터는 기준선으로만 써서 거짓 최고값을 피합니다.

## 프로세스별 디스크 읽기·쓰기

`DiskSnapshot {}`은 매개변수가 없고 응답에는 출처 단조 시계와 최대 8192개 프로세스의 PID, 생성 시간, 누적 읽기 및 쓰기 바이트만 들어갑니다. 전체 프로세스 정보의 경로, 명령줄이나 계정 필드는 전송하지 않으며, 조회에 실패하면 실패 분류와 NTSTATUS만 담은 `DiskFailed`를 반환합니다. 대체 출처는 `SystemFullProcessInformation`의 디스크 카운트 확장으로 일반 I/O와 분리되어 있습니다. 추적 세션을 만들지 않고 드라이버를 로드하지 않으며 시스템 카운트 스위치를 바꾸지도 않습니다.

일반 프로세스 조회가 이미 유효한 디스크 카운트를 제공하면 호스트는 그 결과를 바로 쓰고 서비스 요청을 보내지 않습니다. 그 밖의 경우 `DiskClient`가 독립 스레드에서 읽습니다. 관리자 권한에서는 전체 정보를 조회하고 표준 권한에서는 승인된 서비스를 통해 조회합니다. 샘플링 스레드는 캐시를 읽어 속도만 계산합니다. 캐시가 두 샘플링 간격(이번과 지난 샘플링 중 긴 주기, 창이 전면으로 돌아온 첫 주기는 지난 백그라운드 주기에서 얻은 스냅숏을 사용)에 2초를 더한 시간을 넘거나, 서비스를 쓸 수 없거나, 카운터가 되돌아가거나, 프로세스 신원이 바뀌면 이전 값을 재사용하지 않습니다. 처음 관찰한 경우와 긴 간격(35초 초과, 가장 긴 백그라운드 간격 30초에 샘플링 시각의 흔들림을 더한 값) 뒤에는 기준선을 다시 세웁니다. 이전 스냅숏에 없고 생성 시간이 그 스냅숏의 측정 시각보다 늦은 프로세스는 0을 기준선으로 삼으므로(출처 시계는 `GetTickCount64`이고 로컬 벽시계로 환산) 새 프로세스가 다음 스냅숏에서 바로 속도를 갖게 되며, 이는 일반 프로세스 조회 방식과 같습니다. 머리글과 앱 그룹의 합계는 값을 가진 프로세스만 더하고 모두 없을 때만 없음으로 표시하며, 결측 값을 0으로 계산하지 않습니다.

호스트는 디스크 조회의 실패 출처, NTSTATUS나 Windows 오류 코드, 그리고 기록 범위 초과, 응답 종류 오류 같은 분류를 기록합니다. 원인마다 실행 인스턴스당 한 번 기록하며 최대 8개입니다. 서비스는 응답에 실패 원인을 담습니다. 서비스나 관리자 권한이 없으면 권한 있는 조회를 사용할 수 없음으로 표시합니다. 서비스는 확장 레코드를 해석할 때 경계를 먼저 확인하고 나서 고정 길이 필드를 읽습니다.

## CPU 커널 센서

`SensorSnapshot {}`도 같은 프로토콜 버전과 토큰 검증을 사용하고 추가 필드를 거부합니다. 서비스는 고정된 형식의 온도, 전압, 전류, 전력, 주파수, 제한 상태, 코어별 값, 팬 속도와 메인보드 센서 값을 반환합니다. 모듈, 레지스터와 IOCTL은 모두 서비스 측에 고정되어 있습니다.

모듈은 PawnIO.Modules 0.2.11의 IntelMSR, IntelMCHBAR, AMDFamily10, AMDFamily17, RyzenSMU와 LpcIO로 고정되며 서명된 바이너리를 컴파일 시 포함합니다. [PawnIO 모듈 디렉터리](../../crates/goodgood-service/vendor/pawnio)에는 고정 SHA-256, 업스트림 버전, 완전한 대응 소스와 LGPL 라이선스가 있고, 라이선스 생성 스크립트가 파일 요약도 함께 확인합니다. CPU 호출은 레지스터 읽기와 고정된 SMU 표 위치 확인, 새로 고침 및 읽기만 포함합니다. SMN과 SMU 접근은 `Global\Access_PCI`로 다른 모니터링 도구와 조정하며 대기는 20 ms를 넘지 않습니다. 모듈이 가진 다른 진입점은 IPC에 열지 않습니다.

IntelMCHBAR는 단일 소켓 Comet Lake S/H(Family 6, Model A5h)에서만 Intel 615212-003이 정의한 레이아웃을 사용하며, `5948h`(주파수와 VID), `5980h`(GT 온도), `5998h`(주파수 기능), `5918h`(공유 메모리 클럭), `5848h`/`5858h`(GT/미디어 활동 카운트), `5900h`(제한 상태)를 고정으로 읽습니다. GPU 온도 대신 CPU 온도를 읽지 않고, 레지스터를 쓰거나 래치 상태를 지우거나 GPU를 깨우지 않습니다. 활동 카운트는 9.8/9.9절이 규정한 24 MHz 시간 기준과 샘플링 시간 차이로 계산하고, 실패, 리셋과 너무 긴 간격 후에는 기준선을 다시 세웁니다. 내장 GPU 필드는 `CpuSensors.integratedGpu` 선택적 스냅숏으로 돌려주고, 구버전 서비스에 이 필드가 없으면 사용할 수 없음으로 처리하며 프로토콜 요청은 바뀌지 않습니다. 호스트는 Intel 제조사 ID, PCI `0:2:0`과 유일한 어댑터로 값을 맞추고 외장 GPU나 다중 소켓 시스템에는 보충하지 않습니다.

GPU 페이지는 현재 주파수 필드와 기능 범위를 구분합니다. 주파수 필드가 0이면 코어 주파수와 공유 논리 주파수를 0 MHz로 그대로 표시하며, RC6 휴면과 슬라이스 꺼짐 모두 0 주파수를 만들 수 있습니다. 현재 배율은 9.32절의 공칭 16.666 MHz 단위로, 기능 범위는 9.38절의 50 MHz 단위로 환산합니다. `5918h`의 QCLK 비율은 `[6:0]`이고 참조 선택은 bit 7입니다. 9.41절의 `DCLK = QCLK / 2`로 구성 메모리 클럭을 표시하고 DDR 전송률은 DCLK의 약 두 배입니다. 이 레이아웃에는 확인된 실측 기준 클럭 출처가 없으므로 `5F60h`를 읽지 않고 다른 세대의 `[9:2]`/bit 10 비트 필드도 적용하지 않습니다. GT/미디어 활동률은 Windows 엔진 사용률을 대체하지 않습니다. 내장 GPU의 RAPL 전력은 서비스가 직접 읽은 유효한 PP1 에너지 차이를 우선 사용하고, 없으면 Windows 카운터로 물러납니다. Windows가 0을 보고해도 유효한 직접 값이 있으면 그 값을 우선하며, 제조사 네이티브 값은 원래 우선 순위를 유지합니다.

설정은 기본적으로 꺼져 있습니다. 서비스가 요청을 처음 받으면 이미 설치된 PawnIO 장치를 열고, 수집 스레드는 드라이버를 설치하거나 시작하지 않습니다. 모듈 로드에 실패하면 30초 간격으로 다시 시도하고, 드라이버가 나타나거나 버전이 바뀐 것을 감지하면 즉시 다시 시도하며, 15초 동안 요청이 없으면 모듈을 해제합니다. Intel은 프로세서 그룹별로 수집 스레드의 선호도를 설정하고 복원하며 한 번에 최대 256개 논리 프로세서를 읽고 루프 예산은 500 ms입니다. AMD는 단일 소켓 구성에서 노드 0만 읽고 알 수 없는 CCD / 전압 레이아웃은 추측하지 않습니다. 새로 고치는 동안에는 유효 기간 안의 전체 스냅숏을 재사용하고, 유효한 스냅숏이 없으면 Pending을 반환하며 하위 수집 자체가 만든 NoData와 오류 상태는 그대로 유지합니다. GUI 읽기는 독립 스레드에서 수행하고 샘플링 스레드는 RPC를 기다리지 않습니다.

Intel 패키지 온도, 전력, 전력 제한과 Ring 지표는 독립 스레드가 그룹 0의 논리 프로세서 0에 고정되어 읽습니다. 논리 프로세서마다 작업 스레드를 따로 두고 첫 읽기에서 해당 프로세서에 묶으며 이후 읽기에서 선호도를 유지하고, 최대 256개 논리 프로세서를 덮습니다. 각 스레드는 요청에 따라 새로 고치고 15초 동안 요청이 없으면 모듈과 선호도를 해제하며 무효한 값은 3초 뒤에 비웁니다. 병합할 때는 물리 코어별로 데이터를 묶고, SMT 유효 주파수와 C0 활동률은 형제 스레드가 모두 유효한 값을 가질 때만 평균합니다. 어떤 스레드의 첫 이주가 늦어져도 나머지 코어와 패키지 값은 계속 갱신됩니다.

호스트의 센서 폴링은 현재 샘플링 간격과 무관하게 실행되어, 일반 프로세스/장치 수집이 오래 걸려도 서비스 요청을 멈추지 않습니다. 커널 센서를 끄거나 클라이언트가 종료하면 폴링을 멈춥니다. 샘플링과 캐시 게시에서 잠금 경쟁이 생기면 가장 최근에 얻은 스냅숏과 원래 수신 시각을 그대로 쓰고, 시간 초과 시에는 값을 비웁니다.

스위치를 직접 켜면 호스트는 먼저 권한 있는 서비스가 실행 중이고 승인되었는지 확인한 다음 PawnIO를 검사합니다. 설치나 시작이 필요하면 `--goodgood-sensor-driver-manage`로 독립 UAC 보조 프로그램을 시작합니다. 이 모드는 추가 매개변수, 설치 경로, 다운로드 주소나 사용자 지정 서비스 이름을 받지 않습니다. 고정 패키지는 [PawnIO 2.2.0](https://github.com/namazso/PawnIO.Setup/releases/tag/2.2.0)이고 주소, 크기와 SHA-256은 [설치 패키지 매니페스트](../../crates/goodgood-service/vendor/pawnio/installer.json)에 있습니다. 다운로드는 HTTPS와 고정된 GitHub 릴리스 도메인만 허용하고, 크기와 전체 다이제스트가 일치한 뒤 WinVerifyTrust로 서명과 인증서 해지 상태를 검증합니다.

설치 프로그램은 Program Files 아래 관리자와 SYSTEM만 수정할 수 있는 임시 디렉터리에 쓰고, 실행 전까지 파일을 읽기 전용 핸들로 유지해 교체를 막습니다. 실행 매개변수는 `-install -silent`로 고정합니다. 서로 다른 GoodGood 인스턴스는 설치 잠금을 공유하고, 설치 프로그램이 종료되기를 기다린 뒤 이번에 만든 설치 파일과 디렉터리만 정리하며 드라이버 설치를 중간에 끝내지 않습니다. 그다음 설치 잠금을 삭제하고, 임시 디렉터리의 상위 `GoodGood Sensor Setup`이 비어 있으면 함께 삭제합니다. 시작은 `PawnIO` 커널 서비스만 받아들이고, 보호된 공식 드라이버 위치와 최소 버전을 확인하며 같은 이름의 다른 종류 서비스를 덮어쓰지 않습니다. 호환 버전은 그 서비스에 대응하는 PnP 장치도 확인해야 하며, 서비스와 장치가 모두 정상일 때만 준비된 것으로 봅니다. 장치가 비활성화되어 있으면 장치 관리자에서 활성화한 뒤 다시 시도하도록 안내합니다. 장치 열거에는 `CM_GETIDLIST_DONOTGENERATE`를 사용해 이미 있는 장치 노드만 열거합니다. 시작이 끝나면 고정된 버전 IOCTL로 장치 접근 가능 여부를 확인합니다. 준비 확인 후에만 켜짐 상태를 저장합니다. 스위치를 끄거나 GoodGood을 제거해도 시스템의 공유 PawnIO 드라이버는 유지됩니다. 센서의 구체적인 의미는 [하드웨어 데이터](../guide/hardware-data.md)를 참조하십시오.

공식 2.0.1 설치 패키지의 서명된 드라이버에는 `VERSIONINFO`가 없으므로 `driver/legacy.rs`는 파일 크기와 전체 SHA-256으로 알려진 x64, ARM64 공식 파일을 식별하고, 버전 리소스가 없는 다른 파일은 거부합니다. 마이그레이션은 드라이버가 기본 Program Files\\PawnIO에 있고, 두 레지스트리 뷰에 있는 제거 정보가 모두 이 디렉터리를 가리키며, 버전이 2.0에 속하고, 레지스트리 키의 소유자가 신뢰할 수 있어야 합니다.

Windows 기본 제거 항목 권한에는 Terminal Server User 쓰기 권한이 포함될 수 있습니다. 구버전 제거 프로그램을 실행하기 전에 보조 프로그램은 원래 항목 이름을 임시로 바꾸고, 같은 위치에 관리자와 SYSTEM만 쓸 수 있는 사본을 만들어 모든 값을 복사한 뒤 다시 검증하고 원래 항목을 제거합니다. 키 개체를 교체하므로 이미 가진 쓰기 핸들로 새 사본을 수정할 수 없습니다. 복사에 실패하면 원래 항목을 되돌리려 시도하고, 이름이 이미 쓰이면 백업을 유지하고 중지합니다. 예상하지 못한 하위 키, 레지스트리 링크 또는 그 위치에 먼저 만들어진 다른 키가 있으면 마이그레이션을 멈추고 알 수 없는 레지스트리 내용을 재귀적으로 삭제하지 않습니다.

[공식 2.2.0 설치 프로그램](https://github.com/namazso/PawnIO.Setup/releases/tag/2.2.0)은 2.1.0에서만 직접 업그레이드할 수 있으므로, 2.0 마이그레이션은 새 설치 패키지와 옛 설치 패키지를 준비하고 검증한 뒤 기존 설치를 다시 확인하고 고정된 2.0.1 설치 프로그램으로 `-uninstall -silent`를 실행합니다. 레지스트리의 제거 명령은 실행하지 않습니다. 구버전 설치 프로그램의 주소, 크기와 다이제스트는 `legacy-installer.json`에 고정되어 있고 Windows 서명도 같이 검증합니다. 하위 프로세스의 TEMP/TMP는 보호된 임시 디렉터리를 가리켜 구버전 제거 프로그램이 볼륨을 넘어 파일을 옮기다 실패하지 않게 합니다. 구버전이 반환한 NTSTATUS는 Win32 오류로 변환합니다. 제거가 성공하고 구버전 서비스가 더 이상 없을 때만 2.2.0을 설치하며, 서비스가 아직 사용 중이거나 삭제 대기 중이면 중지하고 재시작을 안내합니다. 다른 모니터링 프로그램을 끝내지 않고 서비스를 강제로 삭제하지도 않습니다.

켜기에 실패하면 호스트는 `goodgood.log`에 읽기 전용 진단 스냅숏을 한 번 덧붙입니다. 현재 권한, 권한 있는 서비스 상태와 승인 결과, PawnIO 서비스 종류와 상태, 시작 유형, 드라이버 경로의 분류, 권한 검사가 이루어진 계층, 숫자 버전, 버전 리소스 크기와 언어/코드 페이지, 원래 파일 이름이 예상과 맞는지, 공식 구버전 다이제스트와 일치하는지, 버전 리소스가 없는 드라이버 파일의 크기와 SHA-256, PnP 장치 수와 시작된 수, 문제 코드와 재시작 대기 표시, 그리고 검증 실패 단계와 오류 코드를 기록합니다. 버전 리소스가 없으면 1 MiB를 넘지 않는 파일에만 다이제스트를 계산하고 넘으면 계속 거부하며, 다이제스트가 일치해도 경로와 제거 정보 검증을 통과해야 합니다. 장치가 재시작 대기로 표시되면 서비스가 아직 실행 중이어도 재시작 후에 다시 켜도록 요구합니다. 스냅숏은 드라이버를 로드하거나 시작하지 않습니다. 드라이버 실제 경로, 거부된 상위 디렉터리나 파일, 실패한 API, 소유자 분류, ACE 인덱스, 종류, 플래그와 권한 마스크를 기록하고, 장치 인스턴스 식별자, 계정 이름이나 리소스의 자유 텍스트는 기록하지 않습니다. 경로는 길이를 제한하고 이스케이프합니다. 작업 당시의 실패와 이후 조회한 현재 상태를 따로 기록해 다시 조회한 결과가 원래 원인을 가리지 않게 합니다.

이미 실행 중인 PawnIO는 고정된 버전 IOCTL로 실제 장치를 먼저 확인하고, 최소 버전을 넘고 PnP 장치가 정상이며 서비스 재확인에서도 실행 중이면 바로 재사용합니다. 표준 권한 호스트는 인증된 권한 있는 서비스의 `Ping` 응답에서 선택적 `sensor_driver_version`을 얻고, 구버전 서비스가 이 필드를 생략하면 드라이버 파일 사전 검사를 그대로 쓰며 새 응답과 옛 응답이 호환됩니다. 재사용 과정은 디스크의 드라이버 파일을 읽거나 로드하지 않고 시스템 디렉터리 권한을 바꾸지 않으며, 로그에 장치 버전과 파일 버전을 따로 기록합니다. 장치가 비활성화되어 있거나 재시작 대기 중이거나 재확인에서 이미 중지되었다면 해당 오류를 유지합니다.

기존 드라이버를 업그레이드하거나 디스크에서 드라이버를 시작할 때 경로 검사는 파일과 각 상위 디렉터리를 모두 덮고, 시작 검사에서 얻은 경로 핸들은 시작이 끝날 때까지 유지합니다. 상위 디렉터리를 일반 사용자가 수정할 수 있으면 이 작업을 중지하고, 오류 메시지에 드라이버 저장 디렉터리에 쓸 수 있음, 드라이버 경로가 안전하지 않음 또는 설치 임시 디렉터리가 안전하지 않음을 각각 표시합니다. 이미 실행 중인 장치를 재사용할 때의 검사 결과는 준비 판단에만 쓰고, 시작 절차는 항상 디스크 경로를 다시 검증합니다.

SMU는 내장된 정확한 버전 레이아웃으로만 해석하고 필드의 유한값과 단위 범위를 검증합니다. 버스가 잠깐 바쁘면 3초 안의 값을 최대한 재사용하며, 전체 표와 물리 주소는 IPC에 넣지 않습니다. 레이아웃 출처와 라이선스는 [CPU 레이아웃 디렉터리](../../crates/goodgood-service/vendor/cpu-layouts)에 있습니다. 코어별 에너지는 물리 코어 단위로 세고 APERF/MPERF는 논리 프로세서에서 샘플링한 뒤 병합합니다. 카운트 초기화, 단위 변화와 너무 긴 간격에는 기준선을 다시 세우고 SMT가 공유하는 전력은 중복해서 더하지 않습니다.

Nuvoton 센서 접근은 `Global\Access_ISABUS.HTP.Method`를 사용하고 대기는 20 ms를 넘지 않습니다. 칩 ID, BAR, 제조사 ID와 고정 레지스터를 모두 검증한 뒤에 읽고, 구성 선택자, 뱅크 선택자와 모니터링 I/O 게이트만 잠시 바꿨다가 원래 값으로 되돌립니다. 인터페이스는 PWM, 팬 곡선이나 임의 포트 쓰기를 제공하지 않습니다. 팬은 하드웨어 채널 번호로 출력합니다. 메인보드 전압과 온도는 메인보드 제조사, 모델과 칩 ID가 일치할 때만 출력하고, 전압은 해당 분압을 사용하며 온도는 멀티플렉서 소스를 먼저 확인한 뒤 고정된 예비 레지스터를 읽습니다. 배터리 모니터링은 펌웨어의 현재 사용 설정 상태를 따릅니다.

## 검증

`cargo test -p goodgood-service`는 임시 명명된 파이프와 직접 만든 하위 프로세스로 통신, 신원과 매개변수 검증, 프로세스 인스턴스 보호, 규칙 실행 순서, 큰 응답, 연결 끊김과 취소를 검증합니다. 느린 실행기와 누적 카운트를 흉내 내 동시성, 규칙 재확인, PID 재사용과 만료 캐시를 검증합니다.

`cargo run -p goodgood-service --example sampling_bridge --release`는 실제 샘플링에 추가되는 큐 제출과 캐시 읽기 비용을 측정하며, 규칙을 구성하거나 서비스를 설치하지 않습니다.

`cargo run -p goodgood-service --example handle_lockers --release -- <절대 경로>`는 같은 격리 절차로 핸들 조회 결과를 출력하며 서비스를 설치하거나 권한 상승을 요청하지 않습니다. 회귀 테스트는 보조 프로세스 종료, 시간 초과 시 이어 찾기, 결과 유지와 인스턴스별 병합을 다룹니다.

## 진단 전달

호스트는 관찰한 서비스 상태 변화에 따라 비정상 종료와 종료 코드를 기록합니다. 같은 중지에 대해 반복 조회하면 원래 상태를 유지하고, 서비스가 다시 시작되거나 정상 중지되었거나 제거된 뒤에 다음 장애를 기록할 수 있습니다. 표준 권한에서 로컬 네트워크 ETW가 권한 부족으로 권한 있는 서비스로 넘어가는 경로는 INFO로 기록하고, 서비스 측이나 관리자 환경에서의 ETW 시작 실패는 계속 경고로 기록합니다.

서비스는 최근 실패 기록 32개를 메모리에 보관하고 각 기록은 최대 4096자입니다. `Ping` 응답이 선택적 필드로 이를 전달하고, 호스트는 서비스 프로세스 신원과 순번으로 중복을 제거한 뒤 `goodgood.log`에 기록합니다. 구버전 서비스는 이 필드를 반환하지 않을 수 있고 구버전 호스트는 이 필드를 무시하며 프로토콜 버전은 바뀌지 않습니다. 네트워크나 센서 읽기에 실패하면 백그라운드 클라이언트가 1분에 최대 한 번 진단을 추가로 조회하고 정상 샘플링은 요청을 늘리지 않습니다. 드라이버 열기, 모듈 로드와 ETW 실패는 원본 오류 코드를 유지하고, 모듈의 선택적 레지스터 읽기는 첫 실패만 기록합니다.

권한 상승 보조 프로그램은 GUI 로그 초기화 전에 실행되므로, 실패 상세는 `%ProgramFiles%\GoodGood Sensor Setup` 아래 관리자 권한으로 보호된 보고서에 기록합니다. 호스트는 시작할 때 얻은 프로세스 핸들로 PID, 생성 시간과 종료 코드를 확인하고 디렉터리와 파일 권한을 검사한 뒤 읽습니다. 보고서를 쓸 수 없으면 보조 프로그램 종료 코드와 보고서 읽기 오류를 함께 보관합니다. 보고서 하나의 상한은 256 KiB이고 최근 16개까지 보관합니다. GoodGood을 제거할 때 제거 훅은 다른 보조 프로그램 뒤에서 `goodgood.exe --goodgood-sensor-setup-remove`를 실행해 이름별로 이 보고서, 설치 잠금과 중단된 설치가 남긴 임시 디렉터리를 삭제하고, 비어 있는 `GoodGood Sensor Setup`을 삭제합니다. 알 수 없는 파일은 유지하고, 다른 세션의 PawnIO 설치가 아직 설치 잠금을 보유하고 있으면 아무것도 바꾸지 않으며, 실패해도 제거를 막지 않습니다. 정리는 설치 잠금을 만들지 않고 잠금 파일 자체만 열며, 잠금 파일이 재분석 지점이나 하드 링크일 때도 아무것도 바꾸지 않습니다. 설정 페이지와 주 프로그램은 여전히 일반 진단 로그만 제공하면 됩니다. 진단 보고서와 작업 결과는 따로 처리하고, 드라이버와 디렉터리는 항상 같은 규칙으로 검증합니다.
