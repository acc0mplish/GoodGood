# 성능 측정

## 측정 조건

측정은 릴리스 빌드, 독립 애플리케이션 식별자와 같은 데이터 원본을 쓰고 창 클라이언트 영역의 물리적 크기, DPI, 새로 고침 간격, 곡선 모드, 장치, 테마와 실제 표시 프레임률을 기록합니다. CPU와 GPU를 비교할 때는 실제 화면과 주기를 같게 유지하고 창 캡처로 측정한 실제 FPS를 기준으로 삼습니다.

다른 머신이나 드라이버와 비교할 때는 Windows 빌드, 디스플레이 드라이버 버전과 HAGS(하드웨어 가속 GPU 예약) 활성 상태를 기록합니다. 활성 상태는 장치 기능 조회나 재부팅 후 DxDiag로 확인하며 그래픽 설정에 저장한 구성은 재부팅 후에 적용됩니다. GPU 주파수, 가장 바쁜 엔진의 사용률과 실제 FPS를 함께 기록하고 스케줄링 모드를 바꾼 경우에는 같은 머신에서 따로 대조합니다. D3D11과 D3D12 작업이 서로 다른 엔진에 나타날 수 있으므로 집계할 때 대상 프로세스의 모든 GPU 엔진을 덮습니다.

tools/window-probe는 Job으로 테스트 프로세스를 추적하고 누적 CPU 시간, 메모리와 GPU 엔진 시간을 샘플링하며 Windows.Graphics.Capture로 대상 창의 표시 간격을 관찰합니다. DWM 소비는 데스크톱 전체의 합성 작업을 포함하므로 따로 기록합니다. 바쁜 개발 머신에서의 프로세스 사용량 결과는 여러 차례 번갈아 측정하고 안정성을 판단해야 합니다.

애플리케이션은 --hidden --test --identifier <독립 식별자>로 시작합니다. 도구는 HWND_BOTTOM과 NOACTIVATE로 표시하고 50 ms마다 포그라운드를 감시합니다. 스크린샷과 프레임 통계는 모두 그 창의 캡처 결과에서 나오며 숨김 상태의 리소스 비용은 따로 측정합니다. 측정이 끝나면 인스턴스를 종료하고 자신의 테스트 데이터를 정리합니다.

이렇게 표시한 테스트 창은 포그라운드에 있지 않으므로 Windows가 그 프로세스에 EcoQoS(전원 제한)를 걸어 하이브리드 아키텍처 프로세서에서 스레드를 효율성 코어로 옮기고 스케줄링 우선순위를 낮출 수 있습니다. 프로브는 자신이 시작한 테스트 프로세스에 `SetProcessInformation`의 `ProcessPowerThrottling`으로 전원 제한을 명시적으로 끄고 다시 읽어 확인하며 실패하면 이번 측정을 거부합니다. 머신이 바쁠 때(예: 병렬 컴파일)는 인터페이스 스레드의 소요 시간이 크게 달라질 수 있으므로 결과를 번갈아 측정하고 그때의 부하를 적습니다.

하이브리드 코어 스케줄링을 제한해야 할 때는 `GOODGOOD_PROBE_PERFORMANCE_CORES=1`을 설정합니다. 프로브는 시스템 토폴로지에서 효율성 등급이 가장 높은 코어를 골라 테스트 프로세스의 선호도만 바꾸고 마스크를 다시 읽어 기록합니다. 이 옵션은 단일 프로세서 그룹으로 제한되고 머신 설정은 바꾸지 않습니다. 결과에는 머신 전체의 사용 정도와 읽을 수 있는 논리 프로세서의 실제 주파수도 기록합니다. 대조할 때는 주파수, 부하, 실제 프레임률과 스케줄링 조건을 맞추고 기본 스케줄링에서의 결과도 덧붙입니다. 조건이 맞지 않은 표본은 따로 보고합니다.

그리기 변경은 긴 프레임, 연속 스크롤 중의 그리기 횟수와 창이 보일 때와 숨겼을 때의 비용으로 대조합니다. 정적 배치나 문구만 다룬 경우에는 영향을 받는 인터페이스만 확인합니다. 원본 결과는 `target/native-validation`에 보관합니다.

## 빌드와 실행

`node scripts/perf-native.mjs <레이블> <EXE 경로>`는 25초 예열 후 프로세스 페이지, CPU 개요, 다중 코어, 정적 설정 페이지와 숨김 상태를 차례로 측정합니다. `--seconds`는 구간마다의 길이를 정하고 `--phases`는 페이지와 곡선 모드를 지정할 수 있습니다. 숨김 상태는 프로브의 `close` 명령으로 닫기 단추를 거쳐 알림 영역으로 들어가며 페이드 아웃을 포함하므로 실제 사용 경로와 같습니다. `--phases`의 `minimized`는 최소화 상태를 측정합니다. CPU는 소속 Job 안의 프로세스를 합산하고 GPU는 물리 어댑터와 엔진별로 소속 프로세스의 실행 시간을 합치며 DWM은 따로 기록합니다. 메모리는 전용 커밋과 작업 집합을 함께 기록합니다. 실제 표시 간격은 창 캡처가 제공합니다.

`--probe`로 프로브 경로를 지정할 수 있습니다. 같은 창 크기와 곡선 모드에서 이전 빌드와 이후 빌드를 번갈아 측정하고 스크린샷과 빌드는 따로 배치하며 회차마다 실제 프레임률을 확인합니다.

`--software-rendering`은 테스트 인스턴스의 설정에서 "하드웨어 가속"을 끄고 창을 WARP가 CPU에서 그리게 하며 결과의 `instrumentation.softwareRendering`에 그 조건을 기록합니다. 기본 모드와 대조할 때는 같은 릴리스 프로그램, 창 크기와 곡선 모드를 쓰고 두 경우의 실제 표시 프레임률을 확인합니다.

`--width`, `--height`는 클라이언트 영역의 물리적 크기를 정하고 `--ui-scale`은 애플리케이션 배율을 백분율로 정합니다(80–150, 기본 100). 유효 배율에는 Windows DPI도 포함됩니다. 물리적 크기 환산에는 0.01 픽셀 미만의 부동 소수점 반올림 오차를 허용합니다. `--no-capture`는 지속적인 창 캡처를 끄며 캡처가 일으키는 합성 경로와 GPU 주파수 변화를 대조할 때 씁니다. 이 모드의 프레임률과 프레임 간격 필드는 `null`이고 리소스 카운트는 정상적으로 기록됩니다. 캡처 결과와 무캡처 결과는 따로 보고합니다.

프로브의 기본 경로는 `target/release/goodgood-window-probe.exe`이며 먼저 `cargo build --release -p goodgood-window-probe --features capture`로 빌드합니다. `--scenario <JSON 경로>`는 단계 배열을 읽으며 각 항목은 `name`, 테스트 제어 객체 `state`를 담고 `seconds`로 그 단계의 길이를 덮어쓸 수 있으며 `hidden: true`로 알림 영역을, `minimized: true`로 최소화를 측정할 수 있습니다(같은 종류의 단계가 연달아 오면 그 상태를 유지하므로 메모리 반환 전후를 대조하기 좋습니다). 또는 `repeat` 배열로 계측 중에 작업을 반복합니다. 반복 작업에는 `app` 테스트 제어, `probe` 프로브 명령과 `waitMs` 대기가 들어갈 수 있고 스크롤, 페이지 전환과 배율 조정에 씁니다. 창을 활성화하는 작업은 보내면 안 됩니다. 결과에는 완전한 시나리오가 남습니다. `--fixture <JSON 경로>`는 고정 스냅숏을 지정하고 결과에는 데이터 파일 요약이 기록됩니다. 연속 곡선을 측정할 때는 고정 스냅숏도 샘플링이나 애니메이션 시간을 명시적으로 진행해야 하며 정지 화면은 정적 시나리오로 따로 측정합니다. 측정과 인터페이스 확인 스크립트는 프로브가 종료된 것을 확인한 뒤 그 식별자의 데이터 디렉터리를 정리합니다.

창 프로브는 독립 테스트 창에 현재 데스크톱보다 큰 클라이언트 영역을 지정할 수 있어 고해상도 배치와 캐시 비용을 다시 확인할 때 씁니다. 실제 클라이언트 영역 크기, 배율과 디스플레이 새로 고침 주기를 기록하고 실물 화면 관찰은 해당 해상도의 테스트 머신을 씁니다.

`--stream-fixture`는 `--fixture`와 함께 쓰며 타임스탬프 묶음 전체를 재생 시작 시각으로 평행 이동하고 예열 중에 1초마다 표본을 하나씩 진행합니다. 정식 측정에서는 시나리오의 `repeat`로 샘플링 빈도를 지정할 수 있습니다. 프로브는 격리 프로세스를 시작하기 전에 작업 전체에 2 GiB 커밋 상한을 설정하고 결과에는 전용 작업 집합, 프로세스 전용 커밋과 작업 커밋 최대값을 따로 기록합니다.

알림 영역 대조에는 `--background-interval 5000`으로 최소화와 알림 영역의 샘플링 간격(밀리초)을 지정하고 `--history`로 기록 쓰기를 유지합니다. 결과에 이 두 조건이 기록되고 기본 간격은 5초이며 테스트 인스턴스의 기록은 기본적으로 끕니다. 메모리를 비교할 때는 전용 커밋과 전용 작업 집합을 따로 보고하고 숨긴 뒤 회수 대기 시간과 다시 표시하는 단계를 두어야 합니다.

## 가상 머신 상호 작용 대조

시작, 백그라운드 호출, 최소화 복원, 정렬과 페이지 전환은 독립 Windows 가상 머신 안에서 측정합니다. `node scripts/build-interaction-bench.mjs`는 상호 작용 프로브와 유휴 프로세스 부하를 빌드하고 `node scripts/prepare-benchmark-guest.mjs`는 릴리스판 GoodGood, Node와 측정 스크립트를 도구 디스크로 묶습니다. 디스크 내용을 가상 머신 안의 쓸 수 있는 디렉터리(예: `C:\GoodGoodBench`)로 복사합니다. 프로브는 상호 작용을 시작하기 전에 QEMU 환경을 확인하고 클라이언트 영역은 모두 1240×800 실제 픽셀을 씁니다.

가상 머신 대조는 정상 시작 경로와 독립 설정 식별자를 쓰고 알림 영역, 프로세스 네트워크 수집, 창 상태, 기록과 우선순위 초기화를 포함합니다. `--control-stdin`은 정상 종료 요청만 받고 끝나면 이번 회차의 네트워크 수집 세션을 회수합니다. 업데이트 확인은 끄고 프로세스 목록은 같은 열 묶음으로 고정하며 구체적인 설정은 환경 기록에 씁니다.

`scripts/configure-vm-ssh.ps1`은 테스트 계정에 Windows OpenSSH 공개 키 로그인을 구성합니다. 가상 머신의 관리자 세션에서 `powershell.exe -NoProfile -ExecutionPolicy Bypass -File C:\GoodGoodBench\scripts\register-vm-desktop-agent.ps1 -Account <테스트 계정>`을 실행해 로그온할 때 시작하는 데스크톱 작업을 등록합니다. 이 작업은 그 계정의 대화형 토큰으로 `vm-desktop-agent.mjs`를 실행하고 API는 `127.0.0.1:18762`에서 수신합니다. 개발 머신에서 SSH 로컬 포워딩을 만든 뒤 그 인터페이스에 접근합니다. 파일 전송과 시스템 명령은 SSH가 맡고 창 조작은 데스크톱 작업이 수행합니다. 테스트 계정은 이미 로그인되어 있고 데스크톱 잠금이 해제된 상태여야 합니다.

| HTTP 인터페이스 | 용도 |
|---|---|
| `GET /status` | 데스크톱 세션, 시스템 버전, 해상도, 최근에 샘플링한 프로세스 수와 현재 측정 단계 |
| `POST /display` | 측정 세션 밖에서 드라이버가 지원하는 해상도를 설정하며 인수는 `width`, `height`입니다 |
| `POST /sessions` | 새 `label`로 격리된 측정 세션을 만듭니다 |
| `POST /queue` | `id`, `tool`, `commands`를 제출하거나 `load`, `stop`을 제출합니다 |
| `GET /report?name=<파일 이름>` | 현재 세션의 JSON 보고서나 컨트롤러 로그를 읽습니다 |
| `GET /frame?run=<요청 ID>&name=<파일 이름>` | 그 작업이 저장한 대상 창 PNG를 읽습니다 |
| `POST /shutdown` | 측정이 끝난 뒤 데스크톱 작업을 종료하며 업데이트나 유지 관리에 씁니다 |

컨트롤러는 GoodGood과 시스템 작업 관리자만 시작합니다. 프로세스 부하는 유휴 프로세스를 최대 1536개까지 늘리며 만드는 동안 사용 가능한 메모리를 최소 2 GiB 유지합니다. 회차마다 실제 프로세스 수, 프로그램 요약과 시스템 환경을 기록하고 끝나면 이번 인스턴스를 종료하고 부하를 회수하며 격리 설정을 정리하고 작업 관리자 설정을 복원합니다. 데스크톱 작업은 남아 있고 새 측정은 새 레이블을 씁니다.

`node scripts/run-vm-bench.mjs <새 레이블>`은 두 회차를 번갈아 대조하며 회차마다 시작, 백그라운드 호출과 복원 표본을 세 번씩 얻고 기본 부하와 유휴 프로세스 512개, 1024개를 더했을 때 정렬과 페이지 전환을 측정합니다. 보고서와 창 화면은 개발 머신의 `target/interaction-validation/<레이블>`로 옮깁니다. 측정 중에는 상태 인터페이스가 컨트롤러의 샘플링을 재사용하고 SSH 파일 전송은 묶음 사이에 배치해 프로세스 목록을 안정적으로 유지합니다. 프로브는 GDI와 USER 객체 수를 함께 기록하고 참조 페이지에 곡선이 없거나 본문이 불완전하면 그 항목을 중단하고 실패 화면을 남깁니다.

`node scripts/lab-vm.mjs <작업> <VM ID>`는 PVE API로 상태, 주소, 전원 조작과 게스트 에이전트를 조회합니다. 스크립트와 서버 쪽 토큰은 모두 할당된 VM ID 120–130으로 제한됩니다. 연결 설정은 기본적으로 사용자 디렉터리의 `.config/goodgood-lab/config.json`에 있고 같은 디렉터리에 `pve-token.json`과 PVE CA 인증서 `pve-root-ca.pem`이 있습니다. `GOODGOOD_LAB_CONFIG`로 다른 설정 위치를 지정할 수 있습니다. 자격 증명은 로컬의 비공개 디렉터리에 보관하고 HTTPS는 CA 검증을 씁니다.

호스트와 게스트의 표준 시간대가 다를 때 `utc-clock`은 Windows의 `RealTimeIsUniversal`과 PVE의 UTC RTC를 함께 설정합니다. 정상 종료 후 다시 시작해야 적용되며 표시되는 시간대는 여전히 게스트 설정을 따릅니다. 디스플레이 장치, 해상도와 시계를 맞춘 뒤 정식 측정 세션을 만듭니다.

시간은 프로세스 생성, 복원 요청이나 입력의 QPC와 Windows Graphics Capture 프레임 타임스탬프를 씁니다. 준비 확인은 창 본문, 뷰포트 가장자리와 아래쪽을 덮고 시작과 복원은 검색 상자에 입력 피드백이 나타났는지도 확인한 뒤 테스트 입력을 지웁니다. 정렬은 PID 방향과 본문 변화를 따로 확인합니다. 매번 완료 프레임을 기록하고 작업 후에는 완전한 화면이 나온 뒤 계속합니다. 백그라운드 호출은 GoodGood을 알림 영역으로 숨긴 상태와 작업 관리자를 최소화한 상태를 각각 쓰고 다시 프로그램을 시작해 창을 불러냅니다. 완전히 종료한 뒤의 시작은 시스템 파일 캐시의 자연스러운 상태를 유지합니다. 시스템 업데이트가 끝나고 부하가 안정된 뒤 두 프로그램을 번갈아 샘플링하며 가상 머신과 실제 머신의 결과는 따로 보관합니다.

`run-vm-bench.mjs <새 레이블> --resume <원래 레이블>`은 중단된 묶음을 이어서 측정합니다. 먼저 애플리케이션 요약, 시스템과 디스플레이 조건을 확인하고 이미 끝난 시작, 복원과 페이지 전환 표본은 유지한 채 정렬은 모두 다시 측정합니다. 묶음마다 출처 묶음과 프로브 요약을 남기고 원래 기록은 따로 유지합니다.

화면을 확인한 뒤 `node scripts/export-vm-bench.mjs <레이블>`은 전체 묶음을 웹사이트 데이터 파일로 내보냅니다. 내보내기는 두 회차의 짝, 표본 수, 완료 화면과 정리 결과를 확인하고 실패했거나 화면이 빠진 묶음은 데이터 파일을 덮어쓰지 않습니다.

## 가속 리소스 테스트

`node scripts/build-leak-tools.mjs`는 테스트용 시계 DLL과 수명이 짧은 부하 프로그램을 빌드합니다. `node scripts/leak-native.mjs <레이블> <EXE 경로> --rate 60 --seconds 60 --rounds 4 --load 600 --observe <서비스 PID>`는 예열, 페이지·테마·대화 상자·표시 전환 반복, 정지와 숨김 단계를 실행합니다. `--rate 1`은 원래 시계로 대조하고, `--capture`는 창의 실제 표시도 함께 기록하며, `--probe`로 프로브 경로를 지정할 수 있습니다.

시계 DLL은 이미 시작한 격리 프로세스에서 주 EXE의 IAT 항목을 바꾸어 QPC, 시스템 시간, 실행 시간과 대기 인터페이스를 덮습니다. Windows, 프로브, 외부 부하와 기존 서비스는 각자의 실제 시계를 유지합니다. `clock.ndjson`은 바꾼 인터페이스, 실제 시간과 가상 시간, 호출 횟수를 기록하고 `resources.json`은 실제 샘플링 순번, 핸들, GDI·USER 객체, 전용 커밋, GPU 로컬·비로컬 상주량과 서비스 카운트를 보관합니다. 유한 대기는 배수만큼 줄지만 하드웨어 수집과 표시는 여전히 실제 처리량에 제약되므로 보고서에 시간 폭과 실제 완료 횟수를 함께 기록합니다.

외부 부하는 결과 디렉터리에 서로 다른 경로로 수명이 짧은 프로세스를 만들고 임시 파일 쓰기와 로컬 루프백 UDP 통신을 수행합니다. `external-load.json`은 완료 수와 받은 바이트 수를 기록합니다. 테스트는 PID와 생성 시간으로 프로세스를 확인하고 서비스는 읽기만 하며 시스템 전체 핸들은 따로 보관합니다. 같은 시나리오의 여러 부하 회차와 정지 후의 잔여량을 비교하고 예열 후 계속 늘어나는 것을 추가 추적의 근거로 삼습니다. 원본 데이터는 `target/native-validation/<레이블>`에 있습니다.

`node scripts/leak-icons.mjs <레이블> <EXE 경로> --probe <프로브 경로>`는 표시 중인 프로세스의 아이콘을 서로 다른 PNG 4,096장으로 돌려 가며 네 회차에 걸쳐 부하와 정지, 숨김 후의 메모리를 기록합니다. 모의 데이터 자체가 메모리에 상주하므로 예열 후의 증가분과 회차별 추세를 비교합니다.

소스의 시간 매개변수 테스트는 메타데이터와 서비스 네트워크 캐시의 시계를 직접 진행시켜 30일에 걸친 항목 생성, 만료와 회수를 다룹니다. 실제 리소스 순환은 따로 실행합니다.

```powershell
cargo test -p goodgood-core thirty_days
cargo test -p goodgood-service thirty_days
cargo test -p goodgood-core resource_soak_icon_extraction -- --ignored --nocapture --test-threads=1
cargo test -p goodgood-service resource_soak_requests_disconnects_and_shutdown -- --ignored --nocapture --test-threads=1
cargo test -p goodgood-service resource_soak_running_service_reads -- --ignored --nocapture --test-threads=1
```

마지막 항목은 이 빌드에 대응하는 권한이 부여된 서비스가 실행 중이어야 하며 고정된 네트워크, 디스크와 CPU 센서 스냅숏을 직접 요청하고 서비스 핸들, 전용 커밋과 종류별 응답 수를 기록합니다. 이 테스트는 드라이버를 설치하거나 서비스 구성을 바꾸지 않습니다.

`cargo test -p goodgood-service slow_native_reads_leave_the_pipe_responsive_and_keep_recent_snapshots -- --nocapture --test-threads=1`은 표준 권한의 독립 파이프로 0.9–1.2초의 하위 읽기를 흉내 내어 동시 응답, 유효한 스냅숏, Ping과 샘플링 진행을 확인합니다. 환경 변수 `GOODGOOD_SERVICE_SOAK_SECONDS=30`을 설정하면 30초로 늘리고 요청 지연, 핸들과 전용 커밋을 기록하며 지연 표본 수에는 고정 상한이 있습니다. `cold_readers_coalesce_waiters_and_keep_ping_available`은 콜드 읽기 동안의 파이프 가용성을 확인하고 캐시 만료, 중지 요청 후의 유휴 비용과 임대 회수는 `snapshot` 모듈 테스트가 다룹니다.

## 고장과 리소스 압박

`node scripts/resilience-native.mjs <레이블> <EXE 경로> --tray-delay 2000 --expect-responsive --capture`는 격리 인스턴스에서 알림 영역 호출을 2초 지연시키고 창 응답과 샘플링 진행을 기록합니다. 고장 경로는 독립 식별자의 `--test` 인스턴스에서만 켜지고 호출은 테스트 수신 측이 처리합니다. 알림 영역 스레드, 막힌 파서 대기열의 용량, 바이트 예산과 재시도에는 각각 소스 회귀 테스트가 있습니다.

`cargo test -p goodgood --lib activation::pressure_tests -- --ignored --nocapture --test-threads=1`은 독립 데스크톱에 응답을 멈춘 항상 위 창을 만들어 활성화, 계층 복원과 기존의 항상 위 상태를 검증합니다. 테스트는 `SwitchDesktop`을 호출하지 않고 실제 데스크톱의 포그라운드를 계속 확인하며 데스크톱과 내부 GUI 보조 스레드는 테스트 프로세스가 끝날 때 회수됩니다.

`node scripts/build-leak-tools.mjs`는 리소스 부하 프로그램도 함께 빌드합니다. `node scripts/pressure-native.mjs <레이블> <EXE 경로> --seconds 20 --headroom-mib 48 --rounds 3`은 기준선, CPU, GPU, 세 라운드의 조합 부하와 복구 상태를 차례로 측정합니다. CPU 부하는 선호도를 고정하고 스케줄링 여유를 남기며 메모리 부하는 시스템의 사용 가능한 메모리를 남기고 GPU는 제한된 CUDA 묶음으로 비디오 메모리 여유를 남깁니다. 결과에는 실제 시스템 CPU와 GPU 엔진 사용률, 애플리케이션 응답, 표시 프레임률, 리소스 카운트와 샘플링 순번이 함께 기록되고 관측한 부하로 적용 범위를 표시합니다.

조합 단계는 애플리케이션 작업의 커밋 상한을 현재 커밋량에 지정한 여유를 더한 값으로 낮추어 할당 공간이 빠듯한 상황을 흉내 냅니다. 이 제한은 테스트 프로세스에만 적용됩니다. 테스트는 또 자신의 인터페이스 스레드를 5초 멈추고 복구 후 응답과 샘플링 따라잡기를 확인합니다. `--probe`로 프로브 경로를 지정할 수 있고 기본값은 개발 프로브이며 성능 대조에는 릴리스판 애플리케이션을 씁니다. 결과와 복구 후 창 스크린샷은 `target/native-validation/<레이블>`에 있습니다.

`--observe <PID 목록>`은 읽기 전용 프로세스 리소스 관측을 덧붙이고 `--service-test <goodgood-service 테스트 EXE>`는 조합 단계에서 기존 서비스의 읽기 전용 압박 테스트를 네 라운드 실행하며 시간 초과, 센서 상태와 서비스 리소스 카운트를 함께 기록합니다. GPU 압박에는 NVIDIA CUDA 드라이버가 필요하고 장치 전체 사용률은 같은 PCI 장치의 NVML 판독값으로 보충하며 부하 프로세스의 엔진 실행 시간은 창 프로브가 기록합니다.

## 프레임 추적과 리소스 카운트

Windows 차트 합성을 확인할 때 같은 릴리스 빌드에 `GOODGOOD_GPUI_DISABLE_CHART_LAYERS=1`을 설정하면 스왑 체인 경로를 측정할 수 있습니다. 진단을 켜면 `gpu-chart-policy`가 장치 기능 조회 결과와 HAGS 활성 상태를 기록하고 `gpu-chart-layers`가 제출한 곡선과 레이어 수를 기록합니다. 지원되는 SDR 환경에서는 `scripts/ui-smoke.mjs`의 `--retained --require-chart-layers` 인수로 레이어 경로의 실제 화면을 확인할 수 있습니다. 정식 리소스 측정에서는 진단을 끄고 애플리케이션 GPU 엔진, DWM, 그래픽 카드 클록과 창의 실제 표시 프레임률을 따로 기록합니다.

HAGS를 지원하는 Windows 11 장치에서 두 스케줄링 모드 모두 기본으로 차트 합성 캐시를 켜고 SDR 출력과 비디오 메모리 예산을 확인합니다. `--require-chart-layers`는 시나리오마다 레이어가 실제로 켜졌는지 확인합니다. `gpu-chart-layers`의 `imageBytes`와 `untrimmedImageBytes`는 각각 잘라 낸 곡선 표면과 전체 그림으로 계산한 바이트 수를 기록합니다. `groupBytes`는 픽셀당 8바이트로 차트 합성 영역의 중간 버퍼를 추정해 예산에 넣습니다. 드라이버의 실제 할당량은 프로브의 프로세스 전용 비디오 메모리 카운트가 기록합니다.

`gpu-frame-clock`은 실제 동기화 원본을 기록하며 Windows 11은 기본적으로 `compositor`를, Windows 10은 `dwm-flush`를 씁니다. 진단할 때 `GOODGOOD_GPUI_USE_DWM_FLUSH=1`을 설정하면 같은 EXE에서 예전 동기화 원본의 표시 주기를 대조할 수 있습니다. 초 단위 GPU 변동은 시나리오의 `probe: "mark tick"`과 1초 대기로 표본을 얻은 뒤 인접한 QPC 시간과 누적 엔진 시간으로 계산하며 그래픽 카드 주파수와 DWM 카운트도 함께 남깁니다.

`gpu-window-surface`는 실제로 만든 스왑 체인의 종류, 형식과 알파 모드를 기록합니다. `gpu-chart-layers`의 `images`는 보이는 곡선 이미지 수이고 `opaqueImages`와 `opaqueStrips`는 배경색과 이미 합성한 이미지 수와 구간 수이며 `imageSheets`는 그 곡선을 담은 텍스처 표면 수입니다. 같은 릴리스 프로그램을 기본 모드와 `--opaque-window`로 각각 시작하고 `GOODGOOD_GPUI_DISABLE_CHART_BACKDROP_CACHE=1`을 설정하면 채워진 곡선을 창 안에서 프레임마다 합성하는 비용을 대조할 수 있습니다. 리소스 대조에서는 창 캡처와 추적을 끄고 실제 프레임률은 창 캡처로 따로 측정합니다. `GOODGOOD_GPUI_FRAME_TRACE=1`만 켜면 같은 시나리오의 그리기 횟수와 Present1 횟수를 비교할 수 있습니다.

프레임률 손실을 추적할 때는 `GOODGOOD_GPUI_FRAME_TRACE=1`을 설정해 표시 동기화, 그리기, 제출, 텍스처 업로드와 텍스트 배치 시점, 그리고 전체 그리기의 단계별 소요 시간을 기록합니다. 이 기록에는 화면 내용이 들어가지 않습니다. `GOODGOOD_GPUI_VIEW_TRACE=1`은 상세 뷰 분석을 함께 켜서 호출 경로를 추적할 때 쓰며 정식 A/B에서는 분석기를 꺼서 추가 비용을 없앱니다. 표시 대기열이 이미 제출한 프레임을 버릴 수 있으므로 실제 표시는 여전히 창 캡처를 기준으로 합니다.

배율을 바꾼 뒤 이전 화면이 남는 현상은 `ui-shots`로 측정합니다. 제목 표시줄 일대(창 위쪽 몇십 행)를 `crop`으로 정하고 그동안 `probe: "size W H"`로 너비를 단계적으로 바꿉니다. 녹화 프레임 시각은 그 프레임이 표시된 시각이며 합성 시각보다 한 번의 새로 고침만큼 늦습니다. 프레임 너비가 이미 새 크기인데 닫기 단추에서 오른쪽 가장자리까지의 거리가 안정된 뒤와 다른 프레임은 새 크기에 이전 내용이 붙은 경우이고, 프레임 너비가 아직 이전 크기인데 단추 위치가 이미 바뀐 프레임은 새 내용이 새 크기보다 먼저 표시된 경우입니다. 프레임 추적의 16단계는 `WM_NCCALCSIZE`에서 미리 그린 클라이언트 영역 크기를, 17단계는 `WM_SIZE`를 기록합니다. `GOODGOOD_GPUI_DEFER_RESIZE_PAINT=1`을 설정하면 같은 EXE에서 `WM_SIZE` 이후에 새 크기를 그리는 동작으로 돌려 대조할 수 있습니다.

`GOODGOOD_GPUI_GPU_TIMING=1`은 D3D11 GPU 타임스탬프 표본을 켜고 작업 17번마다 한 번 표본을 얻으며 최소 4번의 작업 뒤에 읽고 `DONOTFLUSH` 질의를 쓰며 완료되지 않았으면 이후 읽기로 미룹니다. 질의 풀과 로그 대기열은 용량이 고정되어 있고 다 쓰면 표본을 건너뜁니다. `gpu-timing`의 `kind=render`에서 `gpuUs`는 배경 복원, 인스턴스 업로드, 정적 접두부 그리기와 캐시, 동적 접미부 그리기를 차례로 기록하고 `kind=atlas-upload`는 텍스처 할당과 업로드를 기록합니다. `totalGpuUs`는 각 구간의 합이고 `presentCpuUs`는 CPU가 Present1을 호출한 시간을 따로 기록합니다. 각 타임스탬프 묶음은 그 묶음 질의의 `Frequency`로 환산하며 주파수가 유효하지 않거나 카운트가 연속되지 않으면 `valid=false`를 출력합니다. 타임스탬프는 [TIMESTAMP_DISJOINT](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/ns-d3d11-d3d11_query_data_timestamp_disjoint)와 함께 쓰고 결과는 표시 FPS와 따로 해석합니다.

그리기 표본에는 실제 그리기, 배경 복사, 화면 지우기, MSAA 해석의 호출 수와 픽셀 양, 인스턴스와 텍스처 업로드 바이트 수, 변경 영역 면적과 캐시 분기도 기록됩니다. 텍스처 카운트는 인접한 그리기 호출 사이의 증가분이며 그 프레임 전에 준비한 리소스를 포함합니다. 첫 구간에는 렌더링 대상과 파이프라인 상태 준비가 들어가고 타임스탬프 간격에는 GPU 대기열 정지와 리소스 의존 대기가 섞이므로 실제 명령 수와 엔진 사용 시간을 함께 보고 분석해야 합니다. 예를 들어 복사와 화면 지우기 횟수가 모두 0인데 첫 구간 간격이 길면 스왑 체인과 스케줄링 대기를 계속 확인합니다. 텍스처 업로드는 따로 표본을 얻습니다. 진단이 끝나면 이 스위치를 끄고 정식 리소스 대조를 진행합니다.

`gpu-timing.path`는 두 가지 그리기를 구분합니다. `whole`은 동적 접미부가 없는 페이지에 쓰고 이전 프레임과 모든 도형을 비교해 달라진 사각형만 지우고 다시 그립니다. `cached`는 곡선이나 애니메이션 막대가 있는 페이지에 쓰고 정적 접두부를 텍스처에 캐시하고 부분적으로 보수합니다. 둘 다 그 프레임의 스왑 체인 버퍼가 마지막 그리기 이후 놓친 변화를 덧그립니다. `repairedPixels`는 부분 다시 그리기 면적이고 `suffix`는 그 프레임이 동적 접미부를 다시 그렸는지, `localPrimitives`와 `scenePrimitives`는 각각 부분 다시 그리기가 실제로 업로드하고 그린 도형 수와 전체 장면의 도형 수이며 `cpuStepsUs`는 렌더링 함수 각 단계가 끝날 때의 누적 CPU 마이크로초(도형 비교, 컬링, 업로드, 그리기 등)를 기록합니다. `GOODGOOD_GPUI_DISABLE_PREFIX_REPAIR=1`로 같은 빌드에서 정적 전체 그리기를 대조하고 `GOODGOOD_GPUI_DISABLE_SCENE_CACHE=1`은 캐시와 부분 그리기를 함께 끕니다. 프로세스 선택 전환, 포인터를 목록·위쪽·상세 창 위로 계속 움직일 때, 상세 스크롤과 곡선 범위 전환을 각각 측정하며 고정 스냅숏에서 `sample.set`으로 표시값을 바꿀 때는 1초 샘플링 주기를 유지합니다. 범위 테스트에는 전환 종료 후의 안정 구간을 넣어 합성 레이어 복귀, 실제 표시 프레임률과 메모리를 확인합니다.

`gpu-chart-dynamic`은 부분 다시 그리기 표면의 수, 공간과 예산 대체 상태를 기록하고 프레임 추적 9단계는 그 표면의 프레임별 갱신 픽셀 수를 기록합니다. 격리된 `--test` 인스턴스는 `GOODGOOD_GPUI_TEST_DYNAMIC_CHARTS=1`로 이 경로를 강제로 확인할 수 있고 배경색, 불투명도와 예산 검사는 그대로 수행합니다. 고정 데이터로 전체 그리기와 대조한 뒤 실제 프레임률과 리소스 비용을 따로 측정합니다.

`gpu-frame-trace`의 기록 형식은 `[단계, QPC 시간(100 ns), 추가값]`입니다. 0단계는 동기화 신호, 1/2는 그리기 요청 시작·종료, 3/4는 제출 시작·종료, 6은 인코딩 시작, 10/11은 텍스처 업로드, 12/13은 텍스트 배치입니다. 동기화 기록의 추가값은 대기 마이크로초를 두 배 한 값이고 최하위 비트는 슬립 대체를 썼는지 나타냅니다. `frame-phases`는 전체 그리기의 단계별 마이크로초를 따로 제공합니다.

`frame-phases`에는 또 그리기가 끝날 때의 성능 카운터 시간(`atQpc`, 100 ns, 창 캡처와 같은 시계), 뷰 `render` 호출의 총 소요 시간(`renderUs`), 재생한 캐시 뷰 수(`reused`), 이번 프레임에 다시 렌더링한 뷰(`rendered`)와 뷰별 각 단계 소요 시간(`views`)이 들어갑니다. 뷰는 모듈 경로를 뺀 타입 이름으로 기록되고 영역은 `Region<Page>`, `Region<Vitals>`, `Region<Details>`, `Region<Toolbar>`, `Region<Navigation>`입니다. `frame-present`는 제출마다 시각과 소요 시간을 기록합니다. 인터페이스 스레드에서 그리기 외에 0.3 ms를 넘는 작업(명령 결과, 샘플링 처리, 테스트 제어, 행 재구성 등)은 `ui-work-slice`로 기록됩니다. `chart-raster`는 곡선 텍스처마다 물리적 크기, 그리기 스레드 수와 소요 시간을 기록하고 `chart-wait`는 처음 표시하는 차트가 그리기 단계에서 텍스처를 기다린 시간과 그 텍스처가 이 프레임 전에 완성되었는지를 기록합니다. `atQpc`로 이 기록들을 창 캡처의 표시 시각과 맞추면 그리기의 어느 단계, 어느 뷰가 느린지 아니면 그리기 밖이 느린지 구분할 수 있습니다.

`layout-work`는 그 프레임의 레이아웃 노드 수, 루트 레이아웃 횟수, 측정 콜백 횟수와 레이아웃 계산, 측정, 경계 조회와 정리 소요 시간을 기록합니다. 레이아웃 계산 총 소요 시간에는 측정 시간이 이미 포함됩니다. 프로브는 애플리케이션 진단을 완전한 행 단위로 전달해 프레임 표본과 섞이지 않게 하고 해석할 수 없는 구조화 기록이 나오면 측정 스크립트가 원본 출력을 보관하고 실패로 판정하며 빠진 표본을 긴 프레임으로 처리하지 않습니다.

현재 결과 형식은 `measurementVersion: 3`입니다. 단계 경계는 프레임 자신의 QPC 시간을 쓰고 레이아웃 확인은 계측 전의 안정 대기 구간에 둡니다. 프로브는 실제 클라이언트 영역 크기로 창을 보정하고 스크립트는 렌더러 뷰포트도 함께 확인합니다. 서로 다른 회차를 비교할 때는 같은 형식, 실제 크기와 표시 주기를 씁니다.

`uiThreadCpuMsPerSecond`는 해당 창 스레드의 누적 CPU 시간을 기록하며 최적화 전후의 인터페이스 스레드 비용을 추적할 때 씁니다. 애플리케이션 전체 CPU는 여전히 소속 Job의 합산값을 씁니다. `missedRefreshes`는 실제 캡처 간격으로 빠진 새로 고침 주기를 추정하고 가장 긴 간격과 프레임률도 함께 남깁니다.

같은 EXE의 진단 대조에는 `GOODGOOD_GPUI_DISABLE_PREFIX_COMPOSITION=1`로 곡선 배경 합성을 끄고 `GOODGOOD_GPUI_DISABLE_LINEAR_AREA=1`로 미리 곱한 곡선 텍스처를 텍셀별 면적 샘플링으로 바꾸어 하드웨어 선형 샘플링의 비용과 픽셀 결과를 대조할 수 있습니다. `GOODGOOD_GPUI_DIAGNOSTICS=1`의 `gpu-composition-reject`는 합성 대체 이유를 기록합니다. 이 스위치들은 추적에만 쓰며 정식 버전 간 대조에서는 스위치 상태를 기록하고 기본 구성을 사용합니다.

## 인터페이스 대조 시나리오

`scripts/ui-smoke.mjs <식별자> --chart-gap`은 제한된 작업 안에서 여드레 넘게 떨어진 샘플링을 재생하고 CPU 전체 차트, 다중 코어 차트와 프로세스 개요의 곡선 크기 및 병렬 빌드 최대값을 확인합니다. `ui-chart-work.peakRasterBuildBytes`는 비트맵과 마스크의 예약 최대값입니다. `GOODGOOD_GPUI_DIAGNOSTICS=1`에서 `gpu-atlas-page` 이벤트는 종류별 아틀라스 페이지의 실제 생성, 해제, 크기와 바이트 수를 기록합니다. 같은 크기의 빈 페이지를 업로드 단계에서 재사용하면 `gpu-atlas-reuse`로 따로 기록합니다.

`scripts/ui-smoke.mjs <식별자> --chart-scroll --require-chart-layers`는 포인터를 차트 밖에 둔 채 고정된 CPU 최대값을 프레임마다 추적합니다. `--missing-preview`를 덧붙이면 GPU 미리보기에 판독값이 없을 때 다른 곡선이 계속 스크롤되는지, 판독값이 돌아오면 미리보기가 다시 나타나는지 검증하며 정상 샘플링과 샘플링 사이에 전체 프레임 다시 그리기를 끼운 경우를 각각 다루고 되돌린 최대 실제 픽셀 수를 기록합니다. 불투명 창에는 `--opaque-window`를 덧붙일 수 있습니다. 프레임 추적 7단계는 캐시 트리 제출을, 8단계는 같은 루트 노드로 제출한 전체 화면을 기록합니다. GPU 제출 비용을 비교할 때 이 두 항목과 Present1을 따로 셉니다.

`--chart-scroll --clipped-preview`는 여러 장치가 있는 사이드바로 일부만 보이는 작은 그림의 잘라 내기를 검증합니다. CPU 곡선의 정상 스크롤, 추가 그리기와 스크롤한 사이드바에서 잘린 곡선이 다시 나타나는지를 확인합니다. `ui-chart-states`는 차트마다 잘라 낸 범위, 비트맵 범위와 현재 그리기 상태를 나열해 빠른 스크롤을 막는 미리보기를 찾기 쉽게 합니다.

`--retained --require-chart-layers`는 프로세스 개요, 상세, CPU 다중 코어 격자와 각 장치의 성능 페이지에서 스크롤 프레임과 전체 다시 그리기를 비교합니다. `--software-rendering`을 덧붙이면 테스트 인스턴스의 설정에서 "하드웨어 가속"을 끄고 같은 허용 오차로 소프트웨어 렌더링 장치의 레이어 경로를 확인합니다. `gpu-chart-layers.sparseImages`는 가상 표면으로 국소 배경을 보정한 곡선 수를 기록합니다. 다중 코어 페이지에서는 `images`, `opaqueImages`, 실제 표시 프레임률과 프로세스 GPU 사용량을 함께 확인해야 합니다. `--snapshots`는 기록 페이지로 들어가고 전체 다시 그리기를 하고 나오는 과정의 화면을 따로 확인합니다.

`--scroll-copy`는 고정 스냅숏에서 휠로 프로세스 목록을 한 칸씩 스크롤하며(포인터를 목록 위에 두어 마우스 올림 행이 따라 바뀜) 밝은 테마와 어두운 테마, 상세 창, 125%와 150% 인터페이스 배율을 다룹니다. 매번 스크롤이 끝난 뒤 화면을 캡처하고 다시 전체 다시 그리기를 강제한 뒤 캡처하여 두 장이 픽셀 단위로 같아야 하며(소프트웨어 렌더링에서는 글자 가장자리에 두 색 단계까지 허용) 모든 경우에 복사로 그린 프레임이 있어야 합니다. 진단 이벤트 `gpu-scroll-copy`는 복사 프레임마다 옮긴 도형 수, 이동량, 복사와 다시 그리기의 픽셀 수와 잘라 내기 그리기 횟수를 기록합니다. 같은 프로그램에서 `GOODGOOD_GPUI_DISABLE_SCROLL_COPY=1`을 설정하면 복사를 꺼서 스크롤과 페이지 전환의 비용을 대조할 수 있습니다.

표의 행은 기본적으로 GoodGood이 그리며(`tables::body`) 같은 프로그램에서 `GOODGOOD_TABLE_ROWS=component`를 설정하면 구성 요소 라이브러리가 그립니다. 두 그리기를 픽셀 단위로 대조하고 스크롤 프레임의 비용을 비교할 때 씁니다. 행이나 셀의 구조와 스타일을 고친 뒤에는 `ui-shots`로 두 설정에서 같은 단계 파일을 실행하고 스크린샷을 한 장씩 비교합니다.

`--hover-retained`를 덧붙이면 밝은 테마와 어두운 테마에서 위쪽 곡선과 목록 열 설명을 대조할 수 있습니다. `gpu-chart-layers.foregroundBytes`는 전경 캐시 공간을, `foregroundGrouped`는 같은 그룹 합성 경로를 표시합니다. `gpu-chart-foreground-plan`과 거부 이벤트는 그리기 순서와 도형 종류를 추적할 때 씁니다. 성능 시나리오의 `hover` 필드는 레이아웃이 안정된 뒤 포인터를 한 번 설정하고 측정을 시작하므로 정지 상태의 마우스 올림을 관찰하기 좋습니다. 예를 들어 `hover: { hoverChart: "vital-cpu" }`이며 `hoverAt`은 차트 안의 정규화된 위치를 지정합니다.

프레임 추적 14단계는 새 장면이 변하지 않은 합성 트리를 재사용하는 것을 기록합니다. 테스트 제어 `fullPaint`는 플랫폼 렌더링 캐시를 지우고 다시 그리므로 캐시 픽셀 대조의 독립 기준으로 씁니다.

`scripts/ui-smoke.mjs <식별자> --interactions`는 밝은 테마와 어두운 테마에서 행 사이 마우스 올림, 열 설명, 프로세스 선택과 해제, 상세 도움말과 빠져나가기의 화면을 대조하고 포인터 입력만 보냈을 때 그 자리에서 색이 바뀌는 목록 행과 상세 항목(상세 창을 스크롤한 뒤 포인터를 다른 항목으로 옮긴 경우 포함)도 확인합니다. 프레임 추적 15단계는 곡선 범위 밖의 배경 갱신 픽셀 수를 기록하며 이런 국소 변화는 계속 곡선 레이어를 재사용합니다.

프로브의 WinRT 다중 스레드 환경은 프로세스 전체에 걸쳐 유지되고 종료할 때 먼저 캡처를 멈추고 콜백을 등록 해제한 뒤 테스트 창을 닫습니다. `--capture-cycles 50`은 측정 전에 캡처를 반복해서 켜고 끄며 캡처 객체의 정리와 재생성을 확인하고 정식 A/B에서는 이 옵션을 쓰지 않습니다.

`node scripts/ui-smoke.mjs <레이블> --retained --executable <EXE 경로> --probe <프로브 경로>`는 고정 스냅숏으로 프로세스 페이지, CPU 개요와 다중 코어 페이지에서 애니메이션 시간을 진행시키며 부분 갱신과 전체 다시 그리기를 픽셀 단위로 비교합니다. 프로브는 `capture` 기능을 켜서 빌드해야 합니다. 일반 모의 스냅숏 검사는 페이지, 테마, 언어, 정렬과 배치를 덮고 `--live --fluid --move --exercise-updates`는 계속되는 샘플링, 마우스 올림, 창 이동, 배율 조정과 숨김 복원을 확인합니다.

정적 스크린샷은 글꼴 크기의 위아래 한계와 인터페이스 배율도 다룹니다. 포인터를 옮기는 테스트 제어는 그리기 프레임까지 미뤄 실행되므로 캡처 전에 그리기 시간을 따로 두어 남아 있던 마우스 올림 도움말을 시각적 차이로 오인하지 않습니다.

`--snapshots`는 고정 데이터로 샘플링 갱신의 그리기 경계를 확인합니다. 상태 표시줄 값이 실제로 바뀌었는지 확인하고 캐시한 페이지와 전체 다시 그리기를 강제한 결과의 픽셀을 비교하며 센서 상태가 바뀔 때 설정 페이지가 여전히 다시 구성되는지 검사합니다. 페이지와 장치를 전환할 때는 제목과 차트 영역의 밝기 대비도 프레임마다 측정해 페이지, 장치와 GPU 엔진 격자가 처음 표시될 때의 빈 프레임을 잡습니다. 리소스 사용량은 따로 측정합니다.

테스트 제어 `freezeChartGroups`는 영역별로 애니메이션을 멈춥니다. `vitals`는 위쪽 곡선, `details`는 상세 그림, `other`는 그 밖의 차트이며 빈 배열을 넘기면 복구합니다. 샘플링 갱신은 계속 표시값을 바꿉니다. 영역이 같은 그리기 접미부를 공유하면 한 그룹만 멈춰도 그 접미부의 정적 도형이 그려질 수 있으므로 제출 횟수, 변경 영역 면적과 합성 기록을 함께 보고 해석해야 합니다. 렌더러 기하 회귀는 `cargo test --locked -p gpui-pre-windows --lib --target-dir target/rust-analyzer retained_tests`로 실행합니다.
