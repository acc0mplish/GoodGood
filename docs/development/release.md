# 커밋과 릴리스

커밋 메시지는 [Conventional Commits 1.0.0](https://www.conventionalcommits.org/ko/v1.0.0/)을 따르고 버전 번호는 [유의적 버전 2.0.0](https://semver.org/lang/ko/)을 따릅니다. 버전 번호, 한국어 변경 기록 `changelog/ko-KR.md`와 GitHub Release는 모두 커밋 메시지에서 만들어지므로 커밋 메시지의 형식이 릴리스 설명을 그대로 정합니다. `changelog/` 아래 다른 언어의 변경 기록은 `locales/`의 언어 태그로 이름을 붙이며(`en-US.md`, `es-ES.md`, `de-DE.md`, `ja-JP.md`, `fr-FR.md`, `ru-RU.md`) 한국어 판과 항목별로 대응합니다. 즉 `changelog/ko-KR.md`가 원문이고 나머지는 이 파일에서 항목별로 번역합니다. 각 언어의 이름과 소절 제목은 `resources/changelog.json`에서 관리하며 릴리스 스크립트, 애플리케이션과 웹사이트가 이 표로 새 기능, 수정 같은 소절을 구분합니다.

## 지속적 통합

이 저장소는 `.github/`를 포함하지 않으므로 아래 단계를 실행하는 워크플로가 없습니다. 표는 그 워크플로가 하던 일을 순서대로 적은 것이며, 지금은 같은 절차를 `start.bat check`와 `node scripts/release.mjs`로 직접 실행합니다. Windows 빌드와 테스트는 stable MSVC Rust를 사용합니다. 또 [SignPath 테스트 서명 흐름](signing.md#테스트-흐름)이 따로 있습니다.

| 단계 | 실행 시점 | 내용 |
|---|---|---|
| 검사 | 끌어오기 요청, 수동 실행, 릴리스 시 호출 | 커밋 메시지 형식(끌어오기 요청만, 제목 포함), Biome, 문구 검사, 생성 코드 검사, 스크립트 테스트, rustfmt, Clippy, Rust 테스트, 타사 라이선스 고지 최신 여부 |
| 릴리스 | `v*` 태그 푸시 | 태그, 버전 번호, `changelog/ko-KR.md`, 다른 언어의 번역이 끝난 항목과 업데이트 공개 키를 확인하고 태그가 `main`에 있는지 검사합니다. 이어서 위의 검사를 실행하고, 빌드와 애플리케이션 내 업데이트 서명을 마친 뒤 저장소의 공개 키로 서명과 그 안의 버전 번호를 검증합니다. 업데이트 대화 상자에 표시할 업데이트 내용도 서명하고 검증하며, 자동 설치로 제거 항목과 설치 파일, 실행 사본, 포터블 다운로드의 업데이트 유형을 확인한 뒤 자동 제거합니다. 마지막으로 업데이트 매니페스트를 만들고 GitHub Release를 게시합니다 |
| 웹사이트 배포 | 수동 실행(`main`), 또는 릴리스 완료 후 릴리스 단계가 호출 | 게시된 안정판으로 문서와 다운로드 페이지를 빌드하고 두 업데이트 매니페스트를 동기화하며 공개 다운로드, 업데이트 매니페스트, 웹사이트 페이지와 도메인 리디렉션을 항목별로 검증합니다. 설정은 [웹사이트와 릴리스 미러](website.md)를 참고합니다 |

일상적인 커밋과 일반 브랜치 푸시 전에는 변경 범위에 맞는 검증을 마치며 이미 현재 변경을 포함한 결과는 재사용합니다. 문서만 고쳤을 때는 내용과 관련 링크만 확인합니다. 정식 릴리스 전에는 `start.bat check`를 실행하고 `node scripts/notices.mjs --check`로 타사 라이선스 고지를 확인합니다.

## 커밋 메시지

```text
<type>(<scope>)!: <설명>

<본문, 선택 사항>

<꼬리말, 선택 사항>
```

- `type`과 `scope`는 영어 소문자로 쓰고 설명은 한국어로 쓰며 무엇을 바꿨는지 적고 끝에 마침표를 넣지 않습니다. 첫 줄은 100자를 넘지 않습니다.
- 첫 줄과 본문 사이에 빈 줄을 하나 둡니다. 본문은 이유와 영향을 설명하고 변경을 이해하는 데 도움이 되는 구현 세부만 보충합니다.
- 일반 검사, 테스트 또는 빌드의 통과 여부는 커밋 메시지에 쓰지 않습니다. 성능 검증은 짧은 결론이나 핵심 대조 데이터로 요약하고 시험 과정, 원자료 보관 위치나 작업 기록을 나열하지 않습니다.
- 한 커밋은 한 종류의 일만 합니다. 기능, 함께 정리한 리팩터링과 문서는 나누어 커밋하는 편이 좋습니다.

| type | 용도 | 릴리스 설명 포함 | 버전 영향 |
|---|---|---|---|
| `feat` | 새 기능, 사용자가 확인할 수 있는 새 동작 | 새 기능 | 부 버전 |
| `fix` | 결함 수정(끊김, 시각적 흠 포함) | 수정 | 수정 버전 |
| `perf` | 성능 개선 | 성능 | 수정 버전 |
| `revert` | 이전 커밋 되돌리기 | 되돌리기 | 수정 버전 |
| `refactor` | 동작을 바꾸지 않는 리팩터링 | — | 수정 버전 |
| `docs` | 문서만 수정 | — | 수정 버전 |
| `style` | 코드 서식만 수정 | — | 수정 버전 |
| `test` | 테스트만 수정 | — | 수정 버전 |
| `build` | 빌드 스크립트, 의존성, 도구 체인 | — | 수정 버전 |
| `ci` | 지속적 통합 설정 | — | 수정 버전 |
| `chore` | 그 밖의 잡무, 릴리스 커밋 포함 | — | 수정 버전 |

`scope`는 생략할 수 있고 여러 모듈에 걸친 변경에는 쓰지 않습니다. 자주 쓰는 범위는 다음과 같습니다.

| scope | 디렉터리 |
|---|---|
| `core` | `crates/goodgood-core` |
| `service` | `crates/goodgood-service` |
| `host` | `src-gpui` |
| `ui` | `src-gpui/src/frontend` |
| `deps` | 의존성 업그레이드(`build`와 함께 사용) |

예:

```text
feat(ui): 프로세스 페이지에서 열 기준 필터링 지원
fix(host): 창 크기를 조정할 때 나타나던 대각선 흰 줄 수정
perf(core): 프로세스 스냅숏 버퍼 재사용
build(deps): GPUI Kit 업그레이드
docs: 권한 있는 서비스 검증 절차 보충
```

### 호환되지 않는 변경

콜론 앞에 `!`를 붙이고 꼬리말에 `BREAKING CHANGE: <설명>`을 씁니다. 이 설명은 릴리스 설명의 "호환되지 않는 변경"에 따로 나열됩니다. GoodGood에서 호환되지 않는 변경은 업그레이드 후 사용자가 따로 처리해야 하는 변경입니다. 예를 들어 설정이나 기록 데이터 형식이 더 이상 호환되지 않는 경우, 권한 있는 서비스의 IPC 프로토콜을 함께 업그레이드해야 하는 경우, 기능이나 바로 가기 키를 삭제한 경우, 명령줄 인수를 바꾼 경우입니다.

```text
feat(service)!: 권한 있는 서비스가 새 IPC 프로토콜 사용

BREAKING CHANGE: 업그레이드 후 설정에서 권한 있는 서비스를 다시 설치해야 합니다
```

### 커밋 메시지 검사

```bash
pnpm commitlint origin/main..HEAD             # 아직 푸시하지 않은 커밋 검사
pnpm commitlint --message "feat(ui): 새 기능"  # 메시지 하나 검사
```

## 버전 번호

형식은 `주 버전.부 버전.수정 버전`이며 시험판 접미사를 붙일 수 있습니다(예: `1.0.0-beta.1`). 버전을 지정하지 않으면 이전 태그 이후의 커밋으로 추론합니다.

- 호환되지 않는 변경이 있으면 주 버전을 올립니다. 1.0.0 이전(초기 개발 단계)에는 부 버전을 올립니다.
- `feat`가 있으면 부 버전을 올립니다.
- 그 밖의 경우에는 수정 버전을 올립니다.

1.0.0과 시험판 버전은 명시적으로 지정해야 합니다. 버전 번호는 `Cargo.toml`(작업 공간), `Cargo.lock`, `package.json`과 `resources/app.json` 네 곳에 있으며 릴리스 스크립트가 한꺼번에 바꾸므로 직접 고치지 않습니다.

### 테스트 빌드의 버전

커밋에 `v<버전 번호>` 태그가 없는 빌드는 버전 번호 뒤에 SemVer 빌드 메타데이터, 즉 커밋 수와 커밋의 짧은 해시를 붙입니다(예: `0.3.4+583.g4c638d7`). 이 값은 정보 페이지, 상태 표시줄, 업데이트 설정과 진단 로그에 표시되고 EXE의 파일 속성에도 기록됩니다(숫자 파일 버전의 네 번째 항목이 커밋 수입니다). 로직은 `build-support/build-version.rs`에 있습니다.

빌드 메타데이터는 버전 비교에 참여하지 않으므로 테스트 빌드는 `0.3.4`로 처리됩니다. 업데이트 확인, 권한 있는 서비스의 버전 확인과 첫 실행에서 표시하는 업데이트 내용이 영향을 받지 않고 설치 관리자의 제거 항목도 릴리스 버전 번호를 씁니다. 설정, 상태 표시줄 알림과 정보 페이지는 실제 빌드에 따라 개발판, 베타판 또는 안정판을 표시하고 업데이트 채널은 이후 확인의 버전 출처를 따로 정합니다. 설치 관리자 화면, 파일 속성과 설치 패키지 파일 이름은 전체 빌드 식별자를 유지하며 같은 버전을 덮어 설치할 때는 빌드 메타데이터를 무시합니다.

`0.3.4+583.g4c638d7`은 `0.3.4`와 같은 버전 우선순위를 유지하지만 `0.3.4-583`은 시험판 버전이므로 `0.3.4`보다 낮습니다. 릴리스 단계는 `GOODGOOD_BUILD_METADATA`를 비운 뒤 빌드하고 자동 설치 후 EXE의 버전을 확인합니다. 로컬 빌드도 이 변수로 메타데이터를 지정할 수 있고 비우면 붙지 않습니다. 패키징 스크립트는 창 없는 `--goodgood-build-info` 모드로 실제 EXE의 버전과 빌드 종류를 읽고 개발 구성 프로그램이나 패키지 버전과 다른 프로그램을 거부합니다.

## 변경 기록의 내용

스크립트가 커밋으로 만든 항목은 초안일 뿐이므로 릴리스 전에 다음 규칙으로 사용자에게 보이는 변경 기록으로 정리합니다.

- 애플리케이션 안의 기능과 사용자가 분명히 알아차릴 수 있는 변경만 싣습니다. 웹사이트, 지속적 통합, 빌드 스크립트, 테스트와 진단 로그에만 영향을 주는 변경은 넣지 않습니다.
- 이전 버전을 기준으로 삼습니다. 이번 주기에 새로 추가한 기능을 이후에 고치거나 조정했다면 그 기능 항목에 합쳐 최종 동작만 쓰고 수정으로 따로 적지 않습니다. "수정"에는 이전 버전에 이미 있던 문제만 적습니다. 같은 종류의 기능이나 수정은 하나로 합칠 수 있습니다.
- 문어체로 ASD-STE100의 원칙에 따라 씁니다. 짧은 문장, 한 문장에 한 가지, 능동태를 쓰고 용어는 `locales/`의 인터페이스 문구와 맞춥니다. 한 항목은 두세 문장으로 제한하고 길게 늘이지 않습니다.
- 외부 기여자의 끌어오기 요청은 해당 항목 끝에 기여자와 번호를 적고 그 GitHub 프로필과 끌어오기 요청에 각각 링크합니다. 한국어와 다른 언어는 ` ([@사용자 이름](https://github.com/사용자 이름) [#번호](https://github.com/Ray-lea/GoodGood/pull/번호))`로 쓰고 기여자가 여럿이면 `, `로 구분하며, 일본어는 `（[@사용자 이름](…) [#번호](…)）`처럼 전각 괄호를 쓰고 여럿이면 `、`로 구분합니다. 같은 기여자의 끌어오기 요청이 여럿이면 번호를 차례로 나열합니다. 유지 관리자 자신의 끌어오기 요청은 적지 않습니다.
- 항목에 대응하는 issue도 끝에 `https://github.com/Ray-lea/GoodGood/issues/번호`로 링크하고 괄호와 구분자는 위와 같게 씁니다. 한 항목에 기여자와 issue가 모두 있으면 같은 괄호 안에 씁니다.

## 릴리스 절차

1. `main`으로 이동하고 작업 트리를 깨끗하게 만든 뒤 `start.bat check`를 통과시킵니다. 첫 릴리스 전에는 [업데이트 서명 키](#업데이트-서명-키)를 준비합니다. `resources/app.json`에 공개 키가 없으면 스크립트가 릴리스를 거부합니다.
2. 지속적 통합에서 검사를 한 번 실행합니다. [태그를 푸시하기 전에 CI에서 확인](#태그를-푸시하기-전에-ci에서-확인)을 참고합니다.
3. 버전 번호와 각 언어의 릴리스 설명을 미리 봅니다. `pnpm release --dry-run`을 실행하면 다른 언어의 항목을 미리 쓰지 않았을 때 번역 대기 초안이 표시됩니다.
4. 릴리스 커밋과 태그를 만듭니다.

   ```bash
   pnpm release              # 커밋으로 버전 추론
   pnpm release minor        # 또는 단계 지정: major, minor, patch
   pnpm release 1.0.0-beta.1 # 또는 버전 지정
   ```

   스크립트는 로컬에서 네 곳의 버전 번호를 맞추고 한국어 릴리스 설명과 다른 언어의 초안(소절 제목은 이미 해당 언어로 바뀐 상태)을 쓰며 `chore(release): vX.Y.Z` 커밋과 주석 태그 `vX.Y.Z`를 만듭니다. 처음 태그를 만들 때는 기본적으로 현재 버전 번호를 사용합니다.
5. [변경 기록의 내용](#변경-기록의-내용)에 따라 `changelog/ko-KR.md`를 다듬고 다른 언어 파일의 초안을 항목별로 해당 언어로 번역하며 용어는 `locales/<언어 태그>`의 인터페이스 문구와 맞춥니다. 레이블이 붙은 항목은 한국어와 다른 언어에서 `**레이블**: 본문`으로 쓰고 일본어에서는 `**레이블**：본문`처럼 전각 콜론을 씁니다. 한국어와 다른 언어는 콜론 앞에 공백을 넣지 않으며 그래야 애플리케이션이 레이블을 분리합니다. 스크립트가 만든 2단계 버전 제목 `## [X.Y.Z](비교 링크) - YYYY-MM-DD`는 유지하고 항목 안에서는 3단계 제목을 씁니다. 수정한 뒤 `git commit --amend`를 실행하고 `git tag -fa vX.Y.Z -m "GoodGood vX.Y.Z"`로 로컬 태그를 최종 커밋으로 옮깁니다. 각 언어 항목을 미리 커밋해 두고 릴리스 스크립트가 비교 링크와 날짜를 채우게 할 수도 있습니다.
6. 푸시하기 전에 로컬에서 확인합니다. `node scripts/release.mjs verify vX.Y.Z`를 실행하면 릴리스 단계의 첫 검사와 같은 확인을 합니다. 항목을 읽는 규칙은 애플리케이션과 같으므로 다른 언어의 항목이 없거나 한국어 원문이 남아 있거나(링크 주소는 제외하고 일본어는 한글 여부로 판단) 소절과 항목 수가 한국어 항목과 다르거나 날짜가 다르면 통과하지 않습니다. 또 태그가 현재 커밋을 가리키는지, 버전 파일과 각 언어 변경 기록에 커밋하지 않은 변경이 없는지 확인합니다. `node scripts/release.mjs notes X.Y.Z`는 GitHub Release 본문을 출력합니다. 첫 줄은 README와 같은 방식으로 각 언어를 나열하고 한국어와 영어를 굵게 쓰며 나머지 언어는 그 태그의 해당 파일에 있는 버전 항목으로 링크합니다. 그 뒤에 "한국어"와 "English" 두 소절이 온전히 이어집니다.
7. 브랜치와 태그를 푸시합니다. `git push --atomic origin main vX.Y.Z`를 실행하면 릴리스 단계가 곧 검사와 빌드를 시작하고 끝나면 버전이 GitHub Releases에 나타납니다.

푸시하기 전에 취소하려면 `git tag -d vX.Y.Z`를 실행한 뒤 `git reset --hard HEAD~1`을 실행합니다.

릴리스 단계가 실패하면 이미 게시되었는지에 따라 처리합니다.

- **아직 게시되지 않음**: 실패가 "Publish release" 단계 이전(확인, 검사, 빌드, 서명 또는 자동 설치 시험)에서 일어났고 GitHub에 그 태그의 Release가 없으며 매니페스트와 웹사이트도 갱신되지 않은 상태입니다. `main`에 수정을 커밋하고 정상적으로 푸시한 뒤(빠른 진행, `main`의 기록을 다시 쓰지 않음) 태그를 수정한 커밋으로 옮겨 덮어 푸시하면 릴리스 단계가 곧 다시 실행됩니다.

  ```bash
  gh release view vX.Y.Z                            # release not found여야 함
  git push origin main
  git tag -fa vX.Y.Z -m "GoodGood vX.Y.Z"              # 현재 커밋에 릴리스 커밋이 포함되어야 함
  node scripts/release.mjs verify vX.Y.Z
  git push origin +refs/tags/vX.Y.Z:refs/tags/vX.Y.Z
  ```

  실패가 코드와 무관할 때(예: 일시적인 네트워크 오류)에는 실행 화면에서 실패한 작업을 다시 실행해도 되며 태그는 그대로 둡니다.
- **이미 게시됨**: "Publish release"가 실행되어 Release, 매니페스트 또는 웹사이트 중 하나라도 외부에 보인 상태입니다. 태그를 옮기거나 삭제하지 않고 수정한 뒤 새 수정 버전을 릴리스합니다. 문제가 심각하면 [릴리스 후 심각한 문제가 발견되었을 때](#릴리스-후-심각한-문제가-발견되었을-때)에 따라 처리합니다.

### 태그를 푸시하기 전에 CI에서 확인

태그를 푸시한 뒤에는 릴리스 단계가 먼저 검사를 실행하므로 그때 실패하면 수정한 뒤 태그를 덮어 다시 릴리스해야 합니다(위 참고). `start.bat check`에는 릴리스 빌드와 라이선스 고지 확인이 들어 있지 않고 지속적 통합의 환경(영어 Windows, 관리자 계정, 그때의 최신 stable Rust, `--locked`를 붙인 Clippy와 테스트)에서 실행되지도 않습니다. 그래서 `main`을 먼저 푸시하고 그 커밋에 대해 검사 단계를 한 번 수동으로 실행한 뒤 통과하면 `pnpm release`를 실행합니다.

검사 단계는 실행 화면에서 `main`을 대상으로 수동으로 시작하고 끝날 때까지 기다립니다. 이후의 릴리스 커밋은 버전 번호와 `changelog/` 아래 변경 기록만 바꾸며 후자는 6단계에서 로컬로 확인합니다.

릴리스 단계에서 빌드와 게시에 해당하는 부분은 태그를 푸시한 뒤에만 실행되므로 미리 CI에서 확인할 수 없습니다. Secrets의 개인 키로 설치 패키지를 빌드하고 서명하며, 업데이트 내용에 서명하고, 자동 설치와 제거를 수행하고, 매니페스트를 만들고 Release를 업로드합니다. 이 부분을 새로 넣거나 고쳤다면 첫 실행이 곧 정식 릴리스이므로 태그를 푸시한 뒤 그 로그를 확인합니다. 릴리스가 끝나면 `releases/latest/download/latest.json`에서 매니페스트를 받아 버전 번호, `goodgood.releaseNotes`와 `goodgood.signature`를 확인합니다.

## 릴리스 산출물

| 파일 | 설명 |
|---|---|
| `GoodGood_<버전>_x64-setup.exe` | NSIS 설치 관리자이며 관리자 승인을 받아 Program Files에 설치하고 이전 버전을 그 자리에서 업그레이드합니다. 제거할 때 권한 있는 서비스를 함께 제거할 수 있고 시스템 작업 관리자가 복원되었는지 확인합니다. [설치 관리자](#설치-관리자)를 참고합니다 |
| `GoodGood_<버전>_x64.exe` | 포터블 버전 주 프로그램(즉 `goodgood.exe`)입니다. 설치 버전과 같은 설정, 기록과 시작 프로그램을 쓰며 데이터도 `%APPDATA%`, `%LOCALAPPDATA%`에 있고 애플리케이션 내 업데이트를 쓸 수 없습니다. 표준 사용자가 쓸 수 있는 폴더에 두면 권한 있는 서비스를 바꿔치기해 권한을 높일 위험이 있으므로 [설정 → 권한](../guide/settings.md#권한)을 참고합니다 |
| `SHA256SUMS.txt` | 위 두 파일의 SHA-256이며 `sha256sum -c SHA256SUMS.txt`로 검증할 수 있습니다 |
| `latest.json`, `beta.json` | 애플리케이션 내 업데이트 매니페스트이며 안정판에만 있습니다. [업데이트 채널](#업데이트-채널)을 참고합니다 |

시험판 접미사가 붙은 버전은 Pre-release로 표시합니다. GitHub Release 본문에는 한국어와 영어 [코드 서명 정책](../../README.md#코드-서명-정책) 링크가 들어갑니다.

`node scripts/release.mjs notes <버전>`은 버전을 바꾼 뒤 [이중 언어 다운로드 파일 안내](../../scripts/lib/release-downloads.md)를 자동으로 덧붙이고 템플릿의 `{{version}}`을 릴리스 버전 번호로 바꿉니다. 안내는 대조 표로 권장하는 `setup` 설치 버전과 포터블 EXE를 항목별로 비교하며 사용 방식, 버전 업데이트, 바로 가기와 제거 진입점, 권한 있는 서비스와 작업 관리자 대체의 동기화 방식을 담습니다. 정식판과 시험판이 이 생성 진입점을 공유하고 애플리케이션 내 업데이트 내용은 계속 변경 기록의 버전 항목에서 가져옵니다.

## 업데이트 서명 키

Windows Authenticode의 시험 연동은 [Windows 코드 서명](signing.md)을 참고합니다. 시험 서명 흐름은 정식 릴리스와 별개이며 다음 키는 계속 애플리케이션 내 업데이트 검증에 쓰이고 Windows 코드 서명 인증서와 따로 관리합니다.

애플리케이션 내 업데이트는 이 키로 서명한 설치 패키지만 설치하며 서명은 버전 번호(신뢰 주석의 `version:` 필드, 설치 전에 다시 확인)도 함께 덮습니다. 이는 코드 서명과 무관하고 SmartScreen 경고를 없애지 못합니다.

저장소는 기존 릴리스 키, 공개 키와 Actions Secrets를 계속 쓰며 이전 과정에서 새 키를 만들지 않습니다. 릴리스 단계는 기존 Secrets를 GOODGOOD_SIGNING_PRIVATE_KEY와 GOODGOOD_SIGNING_PRIVATE_KEY_PASSWORD로 매핑하고 서명 도구 프로세스 안에서만 읽습니다. 개인 키는 명령줄이나 로그에 쓰지 않습니다.

릴리스 단계는 `goodgood-update-signer`로 최종 설치 패키지에 서명하고 `node scripts/release.mjs check-signature`와 `resources/app.json`의 공개 키로 검증합니다. 로컬에서 설치 패키지를 빌드할 때는 `start.bat build installer`를 씁니다.

업데이트 대화 상자에 표시할 업데이트 내용도 서명합니다. `node scripts/release.mjs release-notes <버전> release-notes.json`은 그 버전과 그 이전 최근 15개 버전의 `changelog/ko-KR.md` 항목을 JSON으로 쓰며, 각 항목에는 `translations`로 언어 태그별 같은 버전의 번역을 붙입니다(아직 초안인 번역은 붙이지 않고 0.3 이전 버전은 이 필드를 무시합니다). 전체 크기가 애플리케이션이 받아들이는 512 KiB를 넘으면 오래된 버전을 생략합니다. `cargo run -p goodgood-update-signer -- <버전> <파일>`은 같은 개인 키로 서명하고 버전 번호를 신뢰 주석에 쓰며 `check-signature`로 다시 검증합니다. 서명 도구는 기존 Base64 개인 키 텍스트를 받으므로 환경 변수에 키의 Base64 내용을 넣어야 합니다. 애플리케이션은 서명 검증을 통과하고 버전 번호가 일치하는 업데이트 내용만 표시하고 인터페이스 언어에 따라 번역을 고릅니다. 해당 번역이 없으면 한국어가 아닌 인터페이스는 영어를 표시하고 영어도 없으면 한국어 원문을 표시합니다.

## 업데이트 채널

GitHub의 최신 안정판 Release는 `releases/latest/download/latest.json`(안정판)과 같은 디렉터리의 `beta.json`(베타판)을 제공하며, 애플리케이션은 GitHub에서만 매니페스트를 읽습니다. 릴리스 절차가 버전과 서명을 검증합니다.

- 안정판을 릴리스하면 두 매니페스트가 모두 이 버전을 가리키며 Release와 함께 업로드됩니다.
- 태그별 검사는 병렬로 실행할 수 있지만 빌드와 게시 작업은 `release-publication` 대기열(`queue: max`)을 공유하여 안정판 릴리스와 베타 매니페스트 쓰기가 뒤섞이지 않게 합니다. 대기 작업은 최대 100개까지 남습니다. 베타판을 릴리스하기 전에는 GitHub asset API에서 현재 매니페스트를 읽어 SemVer로 비교하고 최신 안정판과 현재 베타판보다 버전이 높을 때만 덮어씁니다. 이전 태그가 늦게 끝나거나 다시 실행되어도 이미 게시된 새 버전은 유지됩니다. 현재 매니페스트가 없거나 유효하지 않거나 읽기에 실패하면 게시를 중단합니다.
- 시험판을 릴리스하면 `beta.json`만 그 버전을 가리키게 바꾸어 현재 최신 안정판 Release에 덮어 업로드합니다. 최신 안정판 조회가 분명하게 404를 반환하면 베타 채널은 업데이트를 받지 못하며 릴리스 단계는 경고를 냅니다. 네트워크, 권한 또는 GitHub API 오류는 게시 단계를 실패로 처리하고 안정판이 없는 것으로 보고 건너뛰지 않습니다.
- 매니페스트는 `node scripts/release.mjs manifest`로 만듭니다. `notes`는 `changelog/ko-KR.md`의 해당 항목에서 가져와 일반 텍스트로 바꾸고 커밋 범위(`core`, `ui` 등)를 지운 값이며 0.2 이전 버전의 표시에 쓰입니다. `goodgood.releaseNotes`와 `goodgood.signature`는 앞 절에서 서명한 업데이트 내용 원문과 그 서명이고 새 버전의 업데이트 대화 상자는 이 두 항목만 읽습니다.

자동 경로는 GitHub에 먼저 접속하고, 접속할 수 없으면 가속 프록시를 차례로 시도합니다. 프록시는 GitHub 주소 앞에 접두사를 붙입니다. [설정 → 업데이트](../guide/settings.md#업데이트)를 참고합니다.

## 릴리스 후 심각한 문제가 발견되었을 때

심각한 문제가 있는 버전을 거둘 때는 먼저 각 배포 지점의 업데이트 매니페스트를 되돌린 뒤 더 높은 수정 버전을 릴리스합니다. 자동 업데이트는 현재 버전보다 새로운 패키지만 설치하므로 이미 업그레이드한 사용자는 수정 버전으로 고칩니다.

1. 푸시를 멈춥니다. 문제가 있는 버전을 Pre-release로 바꾸고 이전 안정판을 Latest로 지정한 뒤 애플리케이션이 읽는 매니페스트가 이전 버전으로 돌아왔는지 확인합니다. Release 설명 첫머리에 문제를 적어 둘 수 있습니다.

   ```bash
   gh release edit vX.Y.Z --prerelease
   gh release edit vX.Y.W --latest   # 이전 안정판
   gh release view --json tagName    # 이전 안정판이어야 함
   curl -sL https://github.com/Ray-lea/GoodGood/releases/latest/download/latest.json   # version은 이전 버전이어야 함
   ```

   GitHub의 최신 안정판에는 Pre-release가 포함되지 않으므로 `releases/latest/download/`가 이전 안정판의 `latest.json`과 `beta.json`을 가리키고 이전 버전은 확인할 때 "최신 버전입니다"를 받습니다. 이 두 매니페스트만 삭제하지 마십시오. 주소가 404를 반환하면 확인에 실패한 0.2 이후 버전은 이미 내려받은 업데이트를 유지하고 여전히 설치할 수 있으며, 다운로드 경로가 "자동"이면 가속 프록시로 바꾸어 프록시가 캐시한 이전 매니페스트를 받을 수도 있습니다.
2. 내려받았지만 설치하지 않은 업데이트는 다음 확인이 성공하고 매니페스트가 더 새로운 버전을 제공하지 않을 때 거둡니다. 자동 확인은 시작 후 약 1분에 한 번, 이후 하루에 한 번 실행되므로 그 전까지는 여전히 설치할 수 있습니다.
3. 다운로드 경로가 "자동"이면 GitHub에 먼저 연결하고 GitHub에 접근할 수 있으면 프록시를 거치지 않습니다. 자동 경로는 이어서 가속 프록시를 씁니다. 릴리스를 거둔 뒤에는 웹사이트를 다시 배포해 다운로드 페이지를 최신 상태로 맞추고 필요하면 거둔 파일의 에지 캐시를 지웁니다. 서드파티 프록시는 이전 매니페스트를 유지할 수 있습니다. 서명은 설치 패키지의 무결성을 검증하고 매니페스트의 신선도는 프록시 캐시가 정하므로 이전 매니페스트가 가리키는 설치 패키지가 Release에 남아 있으면 애플리케이션은 그 버전을 계속 내려받습니다. 상황이 심각하면 그 설치 패키지를 삭제할 수 있고(`gh release delete-asset vX.Y.Z GoodGood_X.Y.Z_x64-setup.exe`) GitHub는 곧 404를 반환하지만 프록시가 설치 패키지도 캐시했을 수 있습니다.
4. 수정한 뒤 정상 절차로 수정 버전을 릴리스합니다. 새 안정판이 게시되면 Latest가 되고 두 채널이 모두 그것을 가리키며 문제가 있던 버전은 Pre-release로 남고 태그는 그대로 둡니다.

문제가 있는 것이 베타판이면 1단계가 효과가 없습니다. 베타판은 원래 Pre-release이고 릴리스 단계가 그것을 게시할 때 이미 그 매니페스트를 최신 안정판의 `beta.json`에 덮어썼기 때문입니다(안정판의 원래 `beta.json`은 그때 사라집니다). 대신 최신 안정판에서 `latest.json`을 내려받아(그 안정판을 릴리스할 때의 `beta.json`과 내용이 같음) `beta.json`이라는 이름으로 다시 업로드하고 베타 채널의 매니페스트가 그 안정판으로 돌아왔는지 확인합니다.

```bash
gh release download vX.Y.W --pattern latest.json --dir rollback   # 최신 안정판
mv rollback/latest.json rollback/beta.json
gh release upload vX.Y.W rollback/beta.json --clobber
curl -sL https://github.com/Ray-lea/GoodGood/releases/latest/download/beta.json   # version은 그 안정판이어야 함
```

이후 2단계와 3단계는 베타 채널 사용자에게도 그대로 적용됩니다. 수정 후 새 베타판이나 안정판을 릴리스하면 릴리스 단계가 `beta.json`을 다시 씁니다.

## 설치 관리자

설치와 제거는 다음 두 NSIS 파일이 정의합니다.

- [`installer-template.nsi`](../../packaging/windows/installer-template.nsi)는 설치와 제거 흐름, 서비스 갱신과 데이터 정리를 정의합니다. `scripts/bundle.mjs`가 `resources/app.json`의 메타데이터와 빌드 경로를 넣습니다.
- `packaging/windows/installer-ui.nsh`는 화면 자체입니다. 설치 관리자는 "설치 또는 업그레이드", "진행", "완료" 세 페이지이고 제거 관리자는 "확인(애플리케이션 데이터 삭제 선택 가능)", "진행", "완료" 세 페이지입니다. Windows의 애플리케이션 색 모드에 따라 GoodGood의 밝은 또는 어두운 배색을 쓰고 한국어는 Malgun Gothic, 일본어는 Yu Gothic UI, 그 밖의 언어는 Segoe UI를 쓰며 창 크기는 모든 언어에서 같고 표시 배율에 맞추어 조정합니다. 문구는 각 언어의 `locales/<언어>/installer.json`에서 관리하고 패키징할 때 `scripts/bundle.mjs`가 `installer-locales.nsh`의 `LangString`을 생성합니다.

이전 버전이 설치되어 있으면 설치 페이지에 "버전 X에서 Y로 업그레이드합니다"가 표시되고 먼저 제거하지 않고 덮어 설치합니다(애플리케이션 내 업데이트와 같음). 더 새로운 버전이 설치되어 있으면 단추를 쓸 수 없고 먼저 제거해야 합니다. 자동 모드(애플리케이션 내 업데이트)는 진행 페이지만 표시하고 자동 설치(`/S`)는 화면을 표시하지 않으며 /P, /UPDATE, /R, /ARGS와 /S 인수를 유지합니다.

프로그램을 덮어쓰기 전에 설치 관리자는 자신에서 새 프로그램을 풀어 내부 설치 모드로 주 프로그램을 확인하고 복사합니다. 확인은 프로세스 경로와 생성 시간으로 현재 설치 디렉터리의 GoodGood 인스턴스를 찾은 뒤 그 인스턴스에 따로 종료를 요청합니다. 다른 프로그램이 업데이트를 막으면 대화 상자에 조회할 수 있는 점유 프로세스와 원래 오류 코드를 표시합니다. 복사 단계의 공유 충돌과 메모리 매핑 점유도 같은 진단과 재시도 흐름으로 들어가고 Windows가 점유자 정보를 제공하지 않으면 구체적인 실패 원인을 남깁니다. 점유를 해제한 뒤 "다시 시도"를 누를 수 있고 점유가 풀리지 않으면 취소하면 기존 프로그램 파일은 그대로 남습니다. 자동 모드에서 점유를 만나면 0이 아닌 오류 코드로 끝납니다.

설치 확인 로그는 설치 계정의 `%TEMP%\GoodGood-installer-<임의 식별자>.log`에 기록되고 대화 상자가 구체적인 경로를 알려 줍니다. 로그에는 설치 대상, 실패한 API, 십진수와 십육진수 오류 코드, 점유 프로세스 경로와 재시도 결과가 들어갑니다. 설치 확인마다 로그 파일을 따로 만들어 재시도를 기다리는 동안 바로 읽을 수 있고 로그에 프로세스 명령줄이나 창 제목은 기록하지 않습니다. 계정을 넘어 권한을 높일 때는 대화형 창 스테이션의 로그온 신원으로 원래 데스크톱 계정을 정하고 그 계정에 대해서만 새 로그에 읽기 권한을 주며 기존 권한과 상위 디렉터리 보호는 유지합니다. 권한 설정에 실패하면 구체적인 단계와 오류 코드를 기록하고 설치 계정의 로그는 계속 남깁니다.

NSIS의 `SetCtlColors`는 컴파일 시점의 색만 받으므로 화면은 Windows 강조 색을 따르지 않고 GoodGood의 기본 강조 색을 씁니다. 주 단추와 보조 작업은 Tab／Shift+Tab 탐색을 지원하고 주 단추에는 포커스 테두리, 마우스 올림과 누름 피드백이 있으며 스페이스나 Enter로 실행합니다. 비활성화된 다운그레이드 단추는 키보드 조작에 참여하지 않습니다.

## winget에 게시

웹사이트 빌드는 버전이 들어간 GitHub 설치 패키지 주소와 SHA-256을 쓰는 WinGet 매니페스트 초안을 만듭니다. 유지 관리자가 매니페스트를 검증한 뒤 [wingetcreate](https://github.com/microsoft/winget-create)로 `microsoft/winget-pkgs`에 끌어오기 요청을 보낼 수 있습니다. 생성 위치는 [웹사이트와 릴리스 미러](website.md#메일과-배포-매니페스트)를 참고합니다.
